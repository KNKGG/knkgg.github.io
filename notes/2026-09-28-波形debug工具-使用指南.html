                                                                    RTL 调试 MCP 工具全景 · wave-mcp / TraceWeave / xverif 与底层原理

                                                                    三个主力工具——wave-mcp 走开源 FST 路线、TraceWeave 做端到端调试、xverif 是验证调试工具集，外加一个轻量补充 fsdb-mcp；以及它们共同的底层原理：波形格式、信号追踪、Verdi NPI 与特色算法
                                                                    来源：Tencent/wave-mcp（Apache-2.0，37 工具）· gokeshenzhen/TraceWeave（MIT，38 工具）· BLANK2077/xverif（MIT，10 子工具）· hjxxlogic/fsdb-mcp（轻量，10 工具）· 结论均基于源码（README / pyproject.toml / 核心 .py / .cpp）· 信息截至 2026-09

                                                                    1先搞懂底座：MCP 是什么 概念

                                                                    前面所有工具都叫「MCP Server」，先把 MCP 这个底座讲清楚，后面就全串起来了

                                                                    1.1 一句话本质

                                                                    MCP = Model Context Protocol（模型上下文协议），是 Anthropic 于 2024 年底提出、后来开放给全行业的一个标准，规定「AI 应用」和「外部工具/数据」之间怎么通信。它不是某个软件，而是一份接口规范。

                                                                    1.2 解决什么问题：M×N → M+N

                                                                    没有 MCP 之前，AI 想调用外部工具（读波形、查数据库、访问 GitHub、操作文件），每对「AI × 工具」都要单独写一段对接代码——M 个 AI 应用 × N 个工具 = M×N 份胶水代码。有了 MCP，双方只认这一套标准：工具方实现一次，任何 AI 方都能用。M×N 变成 M+N。这跟做验证用 UVM 是同一个动机。

                                                                    1.3 用验证工程师熟悉的东西类比

                                                                    MCP Server 之于 AI，就像 UVC 之于验证平台。

                                                                    验证领域AI 领域
                                                                    UVM 标准（定义 agent/driver/monitor 接口）MCP 标准（定义 tool 的接口）
                                                                    第三方 UVC（符合 UVM 标准，即插即用）MCP Server（如 wave-mcp，符合 MCP 标准）
                                                                    你的 testbench（UVM 环境，消费 UVC）AI 客户端（Claude Code 等，消费 MCP Server）
                                                                    uvm_driver 通过 vif 驱动信号AI 通过 tool 调用「读信号值」这个能力

                                                                    所以 wave-mcp / TraceWeave / xverif / fsdb-mcp 本质上就是：有人把「读波形、查设计」这件事，按 MCP 标准封装成了几十个工具函数，Claude Code 拿来就能调——就像你拿一个写好的 i2c_agent 插进平台直接用，不用自己从零写时序。

                                                                    1.4 三个核心角色

                                                                    • Client（客户端）：AI 应用，负责「决定要调哪个工具」。Claude Code、Cursor、Codex 都是。
                                                                    • Server（服务端）：能力提供方，负责「真正执行」。wave-mcp、TraceWeave、xverif、fsdb-mcp 都是。
                                                                    • Tool（工具）：最小调用单元——有名字、有参数、有返回值，本质就是一个「可被 AI 远程调用的函数」。

                                                                    通信走 JSON-RPC（JSON 格式的远程过程调用），传输方式就是后文出现的 stdio（子进程标准输入输出）或 HTTP。

                                                                    1.5 最小例子：AI 怎么调用工具

                                                                    {
  "mcpServers": {
    "wave-mcp": {
      "command": "python",
      "args": ["-m", "wave_mcp.server", "--session", "sessions/my_module"]
    }
  }
}
                                                                    ① 你在配置里告诉 AI：「有这个工具服务，用这条命令拉起它」
                                                                    就是上面那段 mcpServers JSON
                                                                    ② AI 启动时按配置拉起 server 子进程
                                                                    stdio 方式，一人一进程
                                                                    ③ server 汇报：「我有 37 个工具，比如 signal_values(paths, ...)」
                                                                    ④ AI 需要查波形时，发 JSON-RPC 请求调用 signal_values
                                                                    传参 paths="top.u_tx.tx_serial"
                                                                    ⑤ server 真正去读 FST，把值算出来返回给 AI
                                                                    ⑥ AI 拿到结果，接着推理
                                                                    「这个信号在 85000ps 变了，说明……」
                                                                    关键点

                                                                    AI 自己并不知道怎么读 FST 文件，它只是「喊了函数名 + 传参数」，真正的读文件动作是 server 干的。MCP 把「AI 会推理」和「工具会干活」这两件事解耦了。

                                                                    2总览：三个主力 + 一个轻量

                                                                    先把四个工具各自是什么、解决什么问题讲清楚，再往下看细节

                                                                    2.1 定位

                                                                    它们都是 MCP Server：把「读波形、查设计」包装成一组标准化工具，让 Claude Code 能像调用函数一样查波形、追 X 态、定位 bug。区别在于波形数据源、要不要商用 License、以及能力的深度。

                                                                    • wave-mcp（腾讯蓬莱实验室，Apache-2.0）：读 FST 波形 + RTL 网表，纯开源技术栈（pylibfst + pyslang），免 License。能力最强：层次探索、信号查询、驱动分析、值/X 态追踪、波形对比、浏览器波形查看器，共 37 个工具。
                                                                    • TraceWeave（gokeshenzhen，MIT）：证据驱动的端到端调试，把编译记录 + 仿真 log + VCD/FSDB 波形 + RTL 源码关联成一条「失败 → 根因」的调查链。三级降级后端（Verdi NPI → pyslang → 源码正则），38 个工具。
                                                                    • xverif（BLANK2077，MIT）：验证调试工具集，C++ 直链 Verdi NPI，10 个子工具覆盖设计/波形查询、SVA 语义、覆盖率、SV 位运算、活会话。强调「确定性」——每个结论带 evidence。
                                                                    • fsdb-mcp（hjxxlogic，社区轻量项目）：用 pynpi 读 FSDB 的最简实现，10 个工具只覆盖「打开 → 浏览 → 查信号值」这条基础链路。（能力上与上面三个主力不是一个量级，只作为轻量补充，详见对比表）
                                                                    一句话定位

                                                                    wave-mcp：开源路线的全能选手，免 License 且能力全。

                                                                    TraceWeave：端到端的「从 log 到根因」调查员，有/无 Verdi 都能用。

                                                                    xverif：确定性优先的工具集，覆盖到 SVA、覆盖率、活会话。

                                                                    fsdb-mcp：最低配的「读 FSDB 值」方案，仅基础读链路。

                                                                    2.2 快速选型表

                                                                    你的情况推荐理由
                                                                    手里是 FST / VCD 波形，或没有 Verdi licensewave-mcp免 License，FST/VCD 开箱即用，能力全
                                                                    想从失败 log 一路追到根因，有 Verdi 环境TraceWeave端到端调试链，三级降级有/无 license 都能跑
                                                                    要覆盖率、SVA 解释、活会话，能接受编译门槛xverif确定性工具集，覆盖验证调试全链路
                                                                    只在已有 Verdi 环境里轻量读一下 FSDB 值fsdb-mcp简单直接，但只有基础读链路

                                                                    3wave-mcp：开源免 License 的波形调试 Apache-2.0

                                                                    腾讯蓬莱实验室验证团队出品，37 个工具 / 12 大类，纯开源技术栈

                                                                    3.1 它是什么

                                                                    一个 RTL 波形调试 MCP Server，读 FST 波形 + RTL 网表，给 LLM 提供波形调试工具集。核心卖点：免 License、数据准确、真实芯片项目背书。

                                                                    • FST 直读，VCD / FSDB 自动转 FST（prepare_session 一步完成，FSDB 转换不占 Verdi license）。
                                                                    • 不跑仿真器：你用自己的流程跑出波形，把结果交给它即可。
                                                                    • 静态分析：用 pyslang 把 RTL 完整精化成一张网表，仿真前就能查连接、驱动、扇入扇出。
                                                                    • 生产级验证：真实芯片项目 + OpenTitan 27 个 IP + 香山 38 个 IP，225 万信号级值查询正确率 100%。
                                                                    两个技术栈各管一半

                                                                    pylibfst 负责读 FST 波形（随机访问、快）；pyslang 负责把 RTL 源码建成网表（提供连接、驱动、扇入扇出这类波形里没有的静态关系）。两者拼起来，才既能查「信号这一拍是什么值」，又能答「这值是被谁驱动的」。

                                                                    3.2 系统要求

                                                                    依赖要求说明
                                                                    Python3.10 – 3.13已测 3.10–3.13 全通过；MCP SDK 要求 ≥ 3.10
                                                                    glibc≥ 2.28pyslang 预编译 wheel 的要求（Ubuntu 18.10+ / Debian 10+ / CentOS 8+）
                                                                    mcp2.x（≥2.0.0,<3）pip install 自动装
                                                                    pylibfst≥ 0.2.1FST 波形读取（fstapi）
                                                                    pyslang≥ 11.0.0RTL 网表构建（完整 elaboration）
                                                                    vcd2fst（可选）GTKWave 附带仅 VCD→FST 转换需要

                                                                    Linux x86_64 开箱即用。其他平台只有 pylibfst 需要源码编译（cmake + gcc + zlib），波形查看器暂不支持。

                                                                    3.3 安装与快速开始

                                                                    # 安装
pip install wave-mcp

# 一条命令：波形(.fst/.vcd) + filelist → session（自动转 FST + 建网表）
wave-session --fst sim/dump.fst --top top_tb --filelist rtl.f

# 启动 MCP Server（stdio，推荐：一人一进程）
python -m wave_mcp.server --session sessions/my_module

                                                                    仓库还带了三个示例，方便跑通流程（examples/ 目录）：

                                                                    • 示例 A Verilator 快启：counter 设计产出真实 FST，跑通 prepare_session 全流程（需 verilator≥5）。
                                                                    • 示例 B 静态分析：UART 设计，无波形、无仿真器，展示仿真前分析。
                                                                    • 示例 C 极小样例：手写 VCD → vcd2fst → FST，零依赖。

                                                                    3.4 CLI 模式

                                                                    不挂 Code Agent 也能在终端直接调全部 37 个工具（与 MCP 同名同参数）：

                                                                    # 列出全部 37 个工具
wave-mcp query --list

# 查询信号值变化
wave-mcp query signal_values --session sessions/my_module \
    --paths top.u_tx.tx_serial

# JSON 传参
wave-mcp query signal_drivers --session sessions/my_module \
    --json-args '{"paths": "top.u_tx.tx_serial"}'

                                                                    参数按工具签名自动生成，wave-mcp query <工具名> --help 查看。默认输出人读文本，加 --json 输出完整结构化结果。适合 CI 脚本、开发调试、快速验证。

                                                                    3.5 接入 Code Agent

                                                                    prepare_session 是 MCP 统一入口：Agent 想分析波形时第一步调它，传入波形，一次完成「（转换 →）建网表 → 建 session → 打开」。

                                                                    prepare_session({
  "wave_path":     "sim/dump.fst",   // .fst 直读 / .vcd 自动转 / .fsdb 自动转
  "top":           "top_tb",
  "filelist_path": "rtl.f",          // 与仿真同一份 filelist
  "pack":          "fastlz"          // 转换压缩：fastlz/lz4/zlib，可省
})

                                                                    各家 Agent 的 MCP 配置（Claude Code 写入 .mcp.json，或 claude mcp add）：

                                                                    {
  "mcpServers": {
    "wave-mcp": {
      "command": "python",
      "args": ["-m", "wave_mcp.server", "--session", "/abs/path/to/sessions/my_module"]
    }
  }
}

                                                                    还有个独家能力 open_static_session：只凭 RTL 源码建网表打开 session，不需要波形、不跑仿真，仿真前就能查接口、驱动、扇入扇出、浏览层次、做 code review。之后仿真出波形，用同一份 RTL 调 prepare_session 升级即可，网表自动复用。

                                                                    3.6 37 个工具 / 12 大类

                                                                    工具按功能分成 12 类，下面列出类别和代表工具：

                                                                    类别代表工具说明
                                                                    波形准备prepare_session / open_static_session / convert_vcd_to_fst / convert_fsdb_to_fst波形入口 → session 一条龙
                                                                    会话管理open_session / close_session / session_infosession_info 含网表健康度 + 覆盖率

                                                                    trace_x：追 X 态根因——沿驱动链反向遍历、跨模块下钻，每个节点带真实 FST 值，直接告诉你 X 是从哪个信号、哪条语句传进来的。diff_waveforms：对 pass/fail 两份波形定位首个分歧时刻，按分歧时间排序信号，配合 signal_fanin 做因果回溯。这是传统 Verdi 手动 debug 很难自动化做的事。

                                                                    3.7 关键环境变量

                                                                    多数人一个都不用配：装完读 FST/VCD、静态分析、波形查看器全开箱可用。只有两种情况需要配：

                                                                    变量要配吗作用
                                                                    VERDI_HOME读 .fsdb 时必配Verdi 安装根目录（不是 bin/），在其下找 share/FsdbReader/linux64
                                                                    WAVE_MCP_TOKENHTTP 跨机时必配HTTP 传输的共享密钥（≥16 字符）
                                                                    WAVE_MCP_SESSION_ROOT建议配session 落点根目录（HOME 有配额时指向本地大盘）
                                                                    WAVE_MCP_CACHE_ROOT建议配派生缓存根目录
                                                                    要配的话，写进 env，不要用 shell 的 export

                                                                    Agent 以子进程方式拉起 Server，继承不到你交互式 shell 里的变量。要把 VERDI_HOME 这类变量写进 MCP 客户端配置的 env 块里才稳定生效：

                                                                    {
  "mcpServers": {
    "wave-mcp": {
      "command": "wave-mcp",
      "env": {
        "VERDI_HOME": "/tools/synopsys/verdi/T-2022.06-SP1"
      }
    }
  }
}

                                                                    3.8 部署模式

                                                                    模式适用说明
                                                                    stdio（推荐）每人本地一人一进程，零运维，不需配置
                                                                    HTTP（本机）本机多客户端python -m wave_mcp.server --transport http --port 8000，绑回环地址不用配 token
                                                                    HTTP（跨机器）别机连过来绑非回环地址必须设 WAVE_MCP_TOKEN，否则拒绝启动

                                                                    3.9 CentOS 7 / 老机器怎么办

                                                                    官方 pyslang wheel 要求 glibc ≥ 2.28，CentOS 7（glibc 2.17）直接 pip install 装不上，会报 GLIBC_2.27 not found。解决办法：

                                                                    • 用 glibc 2.17 档离线 bundle：deploy/docker_build_all.sh 自动在容器内自编兼容 wheel，产出 wave-mcp-bundle-glibc2.17.tar.gz，整条链路（独立 Python + wheel + vcd2fst + 静态 surver）在 glibc ≥ 2.17 均可运行，含 CentOS 7。
                                                                    • 在容器里跑：如 python:3.11-slim，绕开平台差异，最省事。
                                                                    • bundle 自带独立 Python 3.11，与系统 Python 无关，所以目标机 Python 是 3.8 / 3.9 也能用。

                                                                    4TraceWeave：证据驱动的端到端调试 38 工具

                                                                    gokeshenzhen/TraceWeave，MIT，把编译记录 + 仿真 log + 波形 + RTL 源码关联成一条「失败 → 根因」的调查链

                                                                    4.1 它是什么

                                                                    一个证据驱动的 RTL 仿真调试 MCP Server。它把零散的仿真证据——编译记录、仿真日志、VCD/FSDB 波形、层级、RTL 源码、连接关系——整合起来，让 Agent 自主走完这条调查链：

                                                                    哪里失败
                                                                    仿真 log / 编译记录里的 error、timeout、mismatch
                                                                    什么时候失败
                                                                    定位到具体时间窗、接口
                                                                    哪个接口 / 信号异常
                                                                    sweep_handshakes 扫描协议健康度
                                                                    谁驱动它
                                                                    driver / load / path 追踪
                                                                    对应 RTL 在哪
                                                                    回溯到源码文件 + 行号

                                                                    和 wave-mcp「聚焦波形」不同，TraceWeave 的卖点是把 log 和波形、源码三者关联——wave-mcp 不看仿真 log 的 error 定位，TraceWeave 正是从这里切入。

                                                                    4.2 核心能力

                                                                    • GiB 级 log 解析：parse_sim_log 验证过 1 GiB / 200 万行日志，前后中段的 error 全都能找到。
                                                                    • 批量握手检查：sweep_handshakes 一次扫全芯片 valid/ready 与 AHB 接口，返回 stall、死锁、x-while-valid、payload 不保持等事实表（实测 7.8 万信号设计、35 个接口约 4.65 分钟）。
                                                                    • 大设计层级浏览：按需查询 instance / 子树 / 文件，验证过 5 万 instance 的合成设计。
                                                                    • 时序谓词验证：verify_window 支持 always/never/eventually/implication，并区分 overlap 避免空洞通过。
                                                                    • 波形查询 + 驱动追踪：点位/跳变/窗口/周期采样，driver/load/path 查询。

                                                                    4.3 三级降级后端

                                                                    TraceWeave 的核心设计是按「准确度 vs 依赖」做梯度降级——有 license 用最准的，没有就一层层降，绝不硬扛：

                                                                    级后端依赖准确度
                                                                    1VerdiNpiBackendVerdi KDB + license最准（和仿真同源）
                                                                    2Source Graph（pyslang）免 license，但要 pyslang中
                                                                    3StaticConnectivityBackend纯 Python 源码正则，永远可用、不耗 license最低

                                                                    所以「有/无 Verdi license」它都能跑：有 license 走 NPI 精确分析，没 license 退回 pyslang 或纯正则做 log/VCD 分析。详细实现见 6.5 节。

                                                                    4.4 安装与系统要求

                                                                    项目要求
                                                                    Python3.11+
                                                                    core 依赖anyio / mcp==1.27.0 / pydantic>=2.7 / PyYAML（纯 Python，glibc 2.17 大概率可装）
                                                                    pyslang（可选）11.0.0，仅 Source Graph 后端需要
                                                                    Verdi（可选）走 NPI / FSDB 时才需要

                                                                    两种安装：Repository（有 Verdi 环境，FSDB / Source Graph / NPI 全能力）和 PyPI（pip install traceweave-mcp，log / VCD 分析 + 免 license 的 Source Graph）。pyslang 是可选依赖——有 Verdi license 走 NPI 后端就能绕开它，这对 CentOS 7（glibc 2.17 装不上 pyslang）是个关键出路。

                                                                    5xverif：验证调试工具集 确定性

                                                                    BLANK2077/xverif，MIT，C++ 直链 Verdi NPI，工具集 + MCP + skill 三合一

                                                                    5.1 它是什么

                                                                    xverif 不是单一 MCP，而是一个芯片验证调试工具集：底层 10 个 CLI 子工具，中间一个统一 MCP 入口，顶层还带 Claude Code skill（教 AI 怎么 debug）。它强调「确定性」——每个结论带 evidence，语义靠编译不靠 LLM 猜。

                                                                    和其他三个的关键区别

                                                                    wave-mcp / TraceWeave / fsdb-mcp 都只是「MCP Server」；xverif 是工具集 + MCP + skill 三合一。skill 负责「教 AI 怎么 debug」，MCP/工具负责「执行 debug 动作」，这是它独有的。

                                                                    5.2 十个子工具

                                                                    子工具作用
                                                                    xdebug设计 / 波形事实查询（C++ 直链 NPI），驱动/负载/路径 + FSDB 波形
                                                                    xsva把 SVA 时序语义编译成 IR，确定性解释（含空断言 vacuity 检查）
                                                                    xcovVCS/Verdi 覆盖率数据库查询
                                                                    xsimdebug驱动活的 VCS UCLI / Xcelium Tcl 调试会话（打断点、force、单步）
                                                                    xbit纯 Python 的 SystemVerilog 位运算 / 字面量 / 表达式求值器
                                                                    xentry多拍字节片段解码成配置的字段
                                                                    xlocUVM log 源位置压缩 / 还原
                                                                    xwiki验证项目持久知识（skill）
                                                                    xwaveform把波形数据渲染成 JPG + 统计
                                                                    xverif-mcp统一 stdio MCP 入口

                                                                    其中最独特的是 xsimdebug（活会话）和 xcov（覆盖率）——另外三个工具完全没有。活会话让 AI 能像你操作 Verdi 交互调试那样：设断点、force 信号、单步看逻辑。

                                                                    5.3 确定性哲学

                                                                    xverif 的所有命令默认输出 XOUT 结构化文本（@xdebug.trace.driver.v1 这类 header + target:/summary:/evidence:/next: 段），每个回答都带证据来源。设计意图很明确：把「确定性计算」和「LLM 推理」严格分开——查驱动、算位运算、编译 SVA 这些交给工具（确定性），AI 只在确定的事实上做推理（不幻觉）。

                                                                    5.4 安装门槛

                                                                    依赖要求
                                                                    GCC5.0+（编译 C++ 链 NPI）
                                                                    Python3.11+（xverif-mcp / xsva / xcov）；3.10+（xbit 等）
                                                                    VerdiV-2023.12-SP2（开发基准），NPI 签名随版本可能变
                                                                    license需要 Synopsys license（NPI / FSDB / coverage）

                                                                    门槛是四个工具里最高的：要编译 C++、要处理 libstdc++ dual ABI 匹配本地 Verdi 库（make -C xdebug npi-toolchain-check 预检），且作者明说「不保证在所有环境编译」。但它的 Python 依赖全是纯 Python（无 C 扩展 wheel），不吃 glibc 2.17 的坑——对 CentOS 7 反而比 wave-mcp 更容易落地。

                                                                    6底层原理：同一条题的三条解法 深入

                                                                    三个主力工具表面是「让 AI 看波形」，底层其实是同一道题——如何可靠地把「设计结构」和「波形时序」喂给 AI，同时防住 LLM 胡编根因

                                                                    6.1 底层原理地图

                                                                    三个工具定位不同，但底层有三个绕不开的共同地基：

                                                                    1. 波形文件格式解析——都得读波形，但格式不同（VCD / FSDB / FST）；
                                                                    2. 设计网表构建——从 RTL elaborate 出「层次 + 信号 + 连接关系」；
                                                                    3. 信号追踪——debug 的核心：给定一个信号，算出「谁驱动它、它连到哪」。

                                                                    在三块地基之上，每个工具又押注了不同的技术路线：

                                                                    项目特色底层
                                                                    wave-mcppyslang 网表 + 网表自愈；FST 直读 + fsdb2fst 转换器；trace_engine 反向追 X
                                                                    TraceWeave三级后端降级（NPI → pyslang → Legacy Static）；FSDB 走 C++ wrapper；divergence_*.py 波形 diff；handshake_sweep.py 协议扫描
                                                                    xverifC++ 直调 NPI（dispatcher/action 架构）；xsva 把 SVA 编译成 IR；xbit 是纯 Python 的 SV 位运算求值器

                                                                    6.2 波形文件格式：VCD / FSDB / FST

                                                                    这是「随机访问 vs 顺序访问」的分水岭，决定了三条技术路线。

                                                                    VCDFSDBFST
                                                                    性质纯文本（ASCII）Synopsys 私有二进制开源二进制（GTKWave/fstapi）
                                                                    体积最大（FST 的 ~50 倍）GB 级最小（块压缩）
                                                                    随机访问❌ 只能顺序解析✅（经 FSDB Reader）✅ 快（这是它的卖点）
                                                                    谁能读任何工具只能 Synopsys 库开源库（pylibfst）

                                                                    VCD 底层：头部 $var 声明（信号 → 短 ID 码），正文 #时间戳 + 一堆 值 ID码 变化记录。逐行顺序写，读某时刻必须从头扫。

                                                                    FSDB 底层：Synopsys 私有二进制，波形值 + 元数据打包 + 索引支持随机访问，唯一合法读法是调 FSDB Reader 库。

                                                                    FST 底层：波形值按时间块（block）组织，块间双向链表串起来——能前后随机跳转。块内 lz4 / fastlz / zlib 压缩。

                                                                    三个工具各自的读取策略

                                                                    • wave-mcp：统一到 FST——「FST 支持快速随机访问，正好匹配 AI 的点查询工作负载」。VCD 走 vcd2fst、FSDB 走自带的 fsdb2fst，一切先转 FST 再读。
                                                                    • TraceWeave：直接读 FSDB——fsdb_parser.py 用 ctypes 调自己写的 libfsdb_wrapper.so；另有内置 VCD parser 兜底。
                                                                    • xverif：也直接读 FSDB——xdebug 的 C++ 引擎直链 Synopsys 库。
                                                                    最核心的洞察

                                                                    「随机访问 vs 顺序访问」是三条设计分叉的根。人看波形是顺序浏览；AI agent 是大量随机点查询（追 X 要反着跳、diff 要跳到分歧时刻）。所以 wave-mcp 死磕 FST（免 license + 随机访问），TraceWeave/xverif 走 FSDB Reader（借 Verdi 现成的索引）。

                                                                    6.3 信号追踪算法

                                                                    给定一个信号，算出「谁驱动它、它连到哪」——三种实现，正好对应三个工具。

                                                                    工具数据来源追踪方式
                                                                    wave-mcppyslang 自己 elaborate值驱动（value-informed）反向追踪
                                                                    TraceWeave自己编译成 ConnectivityIR纯结构图遍历（不依赖波形值）
                                                                    xverif借 Verdi 已 elaborate 的 KDB直接调 NPI 的 driver/load API

                                                                    wave-mcp：值驱动反向追踪

                                                                    核心是 trace_value / trace_x 两个反向驱动链遍历，关键在结构数据 + 时序数据结合：

                                                                    # trace_engine.py 的 docstring
# Structural data comes from the elaborated netlist (accurate).
# Temporal decisions (which branch / fan-in is active) use FST values
# and are best-effort.
                                                                    • 多驱动冲突检测：用 FST 值做分支守卫（branch-guard）求值，同时 active ≥2 就并行暴露所有驱动（源码 _conflict，注释 bus contention -> X）。
                                                                    • 追 X 的 trace_x：反向走但只沿「该时刻是 X」的扇入走，定位 X 根因。
                                                                    • 识别时序元素：遇到 nonblocking 赋值标注 "latched from a previous cycle"，即它知道自己跨 cycle 追。

                                                                    TraceWeave：纯结构 IR 图遍历

                                                                    不依赖波形值，先把设计编译成 ConnectivityIR 图再做纯图遍历：

                                                                    • 端口/接口绑定 = 透明的层级边（跨模块追踪靠它）；
                                                                    • 源赋值 = 终端的驱动/消费者事实（driver/load 查询查它）；
                                                                    • 有向组合边用于路径查询，但「时序边界从不被跨越」——遇到寄存器就停，不像 wave-mcp 那样跨 cycle 追。
                                                                    三种「拿到驱动关系」的方式 = 三种 elaborate 来源

                                                                    自己 elaborate（pyslang，wave-mcp）：免费可控，但和仿真器的 elaborate 可能有差异；

                                                                    自己编译 IR（TraceWeave）：不依赖波形值、可做置信度分级，但停在时序边界，追不了跨 cycle 的 X；

                                                                    借 Verdi 的 elaborate 结果（xverif）：和仿真器完全一致、最准，但绑死 license。

                                                                    这解释了一个实际现象：追 X 态根因，wave-mcp 的 trace_x 能跨 cycle 沿 X 扇入追（因为它有值），TraceWeave 追到寄存器就停——这是它们 debug 能力的真实边界差，不是宣传话术。

                                                                    6.4 Verdi NPI 接口

                                                                    NPI（Novas Programming Interface） 是 Synopsys Verdi 的编程接口，让第三方程序访问 Verdi 已 elaborate 的设计数据。前提链：设计先用 Verdi/VCS 编译成 KDB → NPI 库（libnpi.so）从 KDB 读网表、驱动/负载、FSDB。

                                                                    关键价值：NPI 读到的驱动/负载和仿真器用同一份 KDB，所以和仿真完全一致——不会像 pyslang「自己再 elaborate 一遍」产生偏差。

                                                                    两种语言绑定

                                                                    TraceWeavexverif
                                                                    绑定方式pynpi（Synopsys 官方 Python 封装）C++ 直接链 libnpi.so
                                                                    调用链Python → pynpi → libnpi.so → KDBC++ 进程（xdebug）→ libnpi.so → KDB
                                                                    好处MCP server 是 Python，无缝集成性能好、可控
                                                                    代价依赖 Verdi 的 Python 环境要编译 C++（GCC 5.0+、libstdc++ ABI）

                                                                    从 npi_dynamic.py 能挖出 NPI 的核心 API——debug 时真正用到的原子操作：

                                                                    net.driver_list()        # 拿一个信号的所有驱动
net.load_list()          # 拿一个信号的所有负载
net.is_generated()       # 是否 Verdi 合成的中间网
net.is_literal()         # 是否字面量（常量）
net.type() == "npiNlConcatNet"  # 是否拼接网 {a,b}

                                                                    关键设计概念：is_generated vs is_literal。Verdi 编译 RTL 时把表达式拆成一堆合成网，TraceWeave 用这属性区分——真实声明的 net 是「观察边界」（停在这里），合成的 net 要展开。

                                                                    有界查询与 LSF

                                                                    NPI 查询有三个硬限制（_MAX_STATES=256/_MAX_DEPTH=32/_MAX_PINS=64），原则是「never a recursive fan-in cone」——顺着一个信号递归展开扇入锥在大 SoC 里会爆炸成几百万个网，所以只做有界单步，超了返回「不完整」标记（ProjectionGap）。

                                                                    还有个环境架构点：NPI 查询要消耗 Verdi license，而 license 在 LSF 计算节点上、MCP server 跑在登录节点，所以 TraceWeave 用独立 worker 进程（npi_worker.py）通过文件传请求，xverif 用 XVERIF_MCP_BACKEND=lsf 通过 bsub -I 送进集群。

                                                                    6.5 各项目特色算法

                                                                    TraceWeave：三级降级 = 准确度 vs 依赖的梯度取舍

                                                                    几个设计细节值得注意：

                                                                    • 没 KDB 就绝不启动 NPI——源码注释原话 starting NPI without a design to load would just consume a license（白烧 license），所以先 probe_verdi_backend 探测。
                                                                    • DeferredConnectivityFallbackBackend 占位符修了一个顺序 bug：让 Source Graph 在 NPI 失败后先于 Static 获得 fallback 机会，降级顺序严格是 NPI → Source Graph → Static。
                                                                    • Static 后端的能力边界诚实标注：find_path 直接返回 static_backend_no_path_api——源码正则做不了路径追踪，不硬编假结果。

                                                                    xverif：SVA→IR 是一个迷你编译器前端

                                                                    xsva/ 目录暴露了一条完整编译管线：

                                                                    frontend/  extractor.py, source.py, macros.py    # 从源码提取 SVA
ir/        expr.py, sequence.py, timeline.py     # 中间表示
lower/     sequence_to_timeline.py, path_expand  # lowering（序列→时间线）
explain/   markdown.py, text.py                  # 解释输出
lint/      rules.py, temporal.py, vacuity.py     # 含空断言(vacuity)检查

                                                                    它把 SVA 时序语义编译成 IR 再确定性解释。为什么是「特色」？因为 SVA 断言（|->、##[1:3]、until）语义极绕，让 LLM 直接解释一定会胡编。xverif 的思路是：语义交给编译器（确定性），不交给 LLM（幻觉）。lint/vacuity.py 还专门查「空断言」——验证工程师最讨厌的坑。

                                                                    wave-mcp：网表自愈 = 让 pyslang 在真实项目里能用

                                                                    slang_netlist.py 遍历 pyslang AST 提取驱动关系（add_driver(lhs, kind, rhs, control)）。而「自愈」是真正的差异化：真实芯片项目的 include 路径极复杂，pyslang 编译经常失败。wave-mcp 的做法是——编译失败 → 读诊断 → 自动补 +incdir+/包源 → 重编；再失败就优雅降级。这就是它能喊出「在香山、OpenTitan 上 100% 通过」的底气。

                                                                    6.6 收束：确定性 vs LLM 推理

                                                                    四块底层收束成同一个思想

                                                                    AI 调试工具要可靠，必须把「确定性计算」和「LLM 推理」严格分开——编译、读值、算驱动这些「算出来的」绝不交给 AI 猜；AI 只负责在确定的事实之上做推理和表达。

                                                                    • wave-mcp 的网表自愈 + 一致性校验：编译、读值这些确定性动作自己扛；
                                                                    • TraceWeave 的置信度分级（EXACT_SOURCE/CONDITIONAL/PARTIAL）：明确标注每个结论多可信；
                                                                    • xverif 的确定性 XOUT + SVA 编译器：每个回答带 evidence，语义靠编译不靠 LLM。

                                                                    它们共同在防一件事：LLM 在 debug 时胡编根因。也因此，这些工具的价值不在于「把单个 case 的调试体验做得比 Verdi 好」，而在于「把确定的事实可靠地喂给 AI，让它做并行、批量、跨工具的推理」。

                                                                    7.2 什么时候选哪个

                                                                    • 优先 wave-mcp：开源路线、能力全、免 License，带 trace_x 和 diff_waveforms 这种自动化 debug 硬能力。除非环境受限（CentOS 7 无 bundle）或要 fsdb 精确读取。
                                                                    • 选 TraceWeave：你想要「从失败 log 一路追到根因」的端到端链路，而不是只盯波形；尤其是有/无 Verdi license 都要能跑的场景。

                                                                    • 选 fsdb-mcp：只是想在已有 Verdi 环境里轻量读一下 FSDB 值，不想折腾 FST 转换或网表。但它只有基础读链路，和上面三个主力不是一个量级。

                                                                    7.3 结论

                                                                    一句话结论

                                                                    想认真让 AI 帮你 debug——追 X 态、找驱动、比波形——首选 wave-mcp（开源免 License、能力全）；要「log→根因」的端到端链路选 TraceWeave；要覆盖率和活会话选 xverif。fsdb-mcp 只是最低配的「读 FSDB 值」方案，作为轻量补充即可，别把它和三个主力等量齐观。
