                                                  RISC-V IOMMU 驱动 · 从零入门路径

                                                  给完全没碰过 Linux 内核源码的人：先认概念 → 再看硬件 → 再学机制 → 最后串成一条完整故事
                                                  源码 drivers/iommu/riscv/：iommu.c（1651 行）· iommu-bits.h（811 行）· iommu.h（91 行）· iommu-pci.c（129 行）· iommu-platform.c（185 行） · 对照 RISC-V IOMMU Architecture Specification v1.0

                                                  1第一站：概念 不碰代码

                                                  这一站的目标：在不读任何代码的前提下，建立对 IOMMU 的直觉和词汇表

                                                  1.1 IOMMU 是什么

                                                  IOMMU = Input/Output Memory Management Unit（输入输出内存管理单元）。它是插在外设和物理内存之间的硬件，功能是：把外设发出的地址（IOVA，I/O 虚拟地址）翻译成真实的物理地址，并检查外设有没有权限访问那块内存。

                                                  类比：写字楼的前台门卫

                                                  物理内存 = 写字楼。CPU = 业主，有自己的门禁（MMU）。外设（网卡/显卡/硬盘）= 访客。

                                                  没有 IOMMU：访客进出不查身份证，网卡说「读写 0x8000」，内存控制器就照做——一个坏掉或被黑的设备可以读走内核机密、写坏系统内存。

                                                  有了 IOMMU：每个访客进门要报「我是哪个设备」（device id），门卫查登记簿（DDT/DC）翻译地址、核对权限。没有登记的访客、越界的访问，一律拦下并记录（fault）。

                                                  1.2 它和 MMU 的关系

                                                  MMU（CPU 用）IOMMU（设备用）
                                                  服务对象CPU 的访存外设的 DMA
                                                  翻译的地址虚拟地址 VA → 物理地址 PAI/O 虚拟地址 IOVA → 物理地址 PA
                                                  页表进程页表（satp 指向）设备上下文 DC 里的页表（fsc 指向）
                                                  出错缺页异常写 Fault 队列 + 中断

                                                  一句话：IOMMU 是「给设备用的 MMU」。如果懂 CPU 的 MMU/页表，理解 IOMMU 会非常快，因为概念几乎一一对应。

                                                  1.3 三个用途

                                                  • 内存保护：只给设备映射它有权访问的内存，坏设备乱写内存会被拦截。
                                                  • 设备直通虚拟化：把设备直通给虚拟机时，用两级翻译（客户地址 → 宿主物理地址）。
                                                  • 地址空间整理：把碎片化的物理内存映射成连续的 IOVA，让设备看到连续地址。

                                                  2第二站：硬件模型 认识零件

                                                  IOMMU 硬件 = 一组寄存器 + 三块内存数据结构。先把零件认全。

                                                  2.1 寄存器：软件和硬件的「对话窗口」

                                                  IOMMU 的控制寄存器映射成一段 4 KB 的内存（MMIO，RISCV_IOMMU_REG_SIZE = 0x1000）。软件读这些地址就是读寄存器、写就是配寄存器。核心寄存器（iommu-bits.h:41-296）：

                                                  偏移名称宽度作用
                                                  0x0000CAPABILITIES64只读能力位图：硬件支持哪些特性（SV39/SV48/SV57、ATS、MSI、IGS 中断模式…）
                                                  0x0008FCTL32特性控制：BE[0] 字节序、WSI[1] 线中断、GXL[2]
                                                  0x0010DDTP64设备目录表指针：MODE[3:0] 目录层级、PPN[53:10] 根表物理页号
                                                  0x0018–0x0044CQ/FQ/PQ 的 Base/Head/Tail—三个队列的基地址和读写指针
                                                  0x0048–0x0050CQCSR/FQCSR/PQCSR32队列控制状态：使能/中断/错误位
                                                  0x0054IPSR32中断挂起状态：4 个位对应 4 类中断
                                                  0x02F8ICVEC64中断源→向量映射
                                                  0x0300MSI_CFG_TBL—平台设备发 MSI 用的配置表

                                                  读能力寄存器的典型用法：硬件上电后，软件先读 CAPABILITIES，看它支持 SV39 还是 SV48、支持 MSI 还是 WSI，再据此配置。fctl 是少数几个可写的寄存器之一（其余大多是只读或需要特殊序列）。

                                                  2.2 数据结构①：设备目录表 DDT + 设备上下文 DC

                                                  这是「访客登记簿」。DDT 是一个多级表（最多 3 级），根地址在 DDTP 寄存器。逐级下钻后落到叶子节点 = 设备上下文 DC。

                                                  DDTP 寄存器
                                                  根表指针（第 1 级）
                                                  表项[DDI[0]]：下一级表地址 + V
                                                  第 2 级表
                                                  表项[DDI[1]]：下一级表地址 + V
                                                  第 3 级表
                                                  表项[DDI[2]]：指向设备上下文 DC
                                                  DC 设备上下文（32 或 64 字节）
                                                  tc 翻译控制（开关）· ta PSCID（进程号）
                                                  fsc 一级页表指针 · iohgatp 二级页表指针（虚拟化）

                                                  DC 结构体（iommu-bits.h:326-335）和关键字段：

                                                  struct riscv_iommu_dc {
    u64 tc;        // 翻译控制：V[0]=有效位（总开关）
    u64 iohgatp;   // 二级页表（虚拟化用，普通场景 = BARE 关闭）
    u64 ta;        // 翻译属性：PSCID[31:12] 进程号
    u64 fsc;       // 一级页表：PPN[43:0] + MODE[63:60]（SV39/SV48/SV57）
    // 以下 4 个字段仅 extended 格式（MSI_FLAT）才有，做 MSI 虚拟化
    u64 msiptp, msi_addr_mask, msi_addr_pattern, _reserved;
};

                                                  两个最容易混的概念：

                                                  • tc.V（BIT 0）= 总开关：等于 0 时，这个设备发任何 DMA 都会被拒绝（fault cause 258 DDT_INVALID）。驱动「阻断」设备就是清这个位。
                                                  • ta.PSCID（bit 12–31）= 进程号：一个 20 bit 的软件编号，用于给 IOTLB 缓存条目贴标签，失效时按它精准清除。范围 1..2^20-1，驱动用 IDA 分配器管理。

                                                  2.3 数据结构②：页表

                                                  页表负责「IOVA → 物理地址」的映射，和 CPU 页表一样是多级结构。RISC-V 用 4 KiB 页、每级 9 bit 索引：SV39 三级（39 bit 地址）、SV48 四级、SV57 五级。

                                                  关键：驱动不手写页表，复用内核通用页表库 generic_pt（pt_iommu_riscv_64）。驱动只告诉库「用 SV39/SV48/SV57 哪种模式」，PTE 的分配/填充/释放由库完成。这是 Linux IOMMU 驱动的常见分工：页表是通用件。

                                                  2.4 数据结构③：两个队列 CQ 和 FQ

                                                  DDT 和页表是「静态数据」，但运行时还有两类「动态通信」：

                                                  队列方向承载什么例子
                                                  命令队列 CQ软件 → 硬件维护命令（16 字节/条）「刷新 IOTLB」「失效目录缓存」
                                                  Fault 队列 FQ硬件 → 软件错误事件（32 字节/条）「设备 3 访问了没映射的地址」

                                                  两条队列都是环形缓冲区，各配一组寄存器：Base（基地址+长度）、Head（读指针）、Tail（写指针）、CSR（控制状态）。队列的长度是 2 的幂（命令队列默认 8192 条、Fault 队列 4096 条）。

                                                  命令的格式：16 字节 = 两个 u64，第一个 u64 的低 7 bit 是 opcode（iommu-bits.h:459-462）：

                                                  opcode名称作用
                                                  1IOTINVAL失效 IOTLB 翻译缓存
                                                  2IOFENCE同步屏障，等前面命令执行完
                                                  3IODIR失效设备目录/进程目录缓存
                                                  4ATSPCIe ATS 相关

                                                  Fault 记录的格式（32 字节 = 4 个 u64，iommu-bits.h:543-548）：头部 u64 里有 CAUSE[11:0]（原因码）、DID[63:40]（发起设备 id）、TTYP[39:34]（读/写/取指类型），后面两个 u64 是出错地址等附加信息。

                                                  第二站小结：硬件 = 一组寄存器 + 三块内存

                                                  寄存器是「控制面板」，DDT/DC 是「登记簿」，页表是「翻译字典」，命令队列是「对讲机（软件对硬件说话）」，Fault 队列是「报警器（硬件对软件说话）」。记住这五个零件，后面都是围绕它们展开。

                                                  3第三站：软件机制 学会操作

                                                  软件怎么读写寄存器、怎么操作队列、怎么发命令

                                                  3.0 一个驱动，如何管多颗 IOMMU？

                                                  先破一个误解：Linux 的「驱动」不是一个运行中的进程或对象，而是 一份代码 + 每个硬件一个数据结构。系统里有几颗 IOMMU，就有几个 struct riscv_iommu_device，各自独立、互不干扰；而操作它们的函数代码，内存里只有一份。

                                                  用 UVM 的话说

                                                  C 语言没有 class，但 Linux 驱动用 struct 模拟了同样的「对象」概念：

                                                  UVMLinux 驱动
                                                  class iommu_agent 定义（一份代码）驱动代码 iommu.c（一份）
                                                  new("agent0") 实例化devm_kzalloc 分配一个 struct（每个硬件一次）
                                                  成员变量 this.reg_value字段 iommu->reg、iommu->caps
                                                  方法 write_reg()函数 riscv_iommu_init(iommu)
                                                  agent0.write_reg() 只改 agent0riscv_iommu_init(A) 只操作 A 这颗硬件

                                                  方法（代码）共享，成员（数据）独立。UVM 里一个 class 能 new 出无数个 agent，每个 agent 的成员互不影响；Linux 驱动里一份代码，probe 每发现一颗 IOMMU 就 new 出一个 struct。

                                                  实际发生的事：probe 被调用几次

                                                  主板上有两颗 IOMMU 时，内核扫描 PCI 总线发现两颗，PCI 框架的规则是匹配到几个设备，probe 就回调几次（iommu-pci.c:33）：

                                                  iommu = devm_kzalloc(dev, sizeof(*iommu), GFP_KERNEL);  // new 一个实例
iommu->dev = dev;
iommu->reg = pcim_iomap_table(pdev)[0];                 // 记下"这颗"的寄存器地址
...
return riscv_iommu_init(iommu);                          // 初始化"这颗"

                                                  第一次调用时 pdev 是 IOMMU A，分配出文件夹 A；第二次是 IOMMU B，分配出文件夹 B。同一段代码跑两遍，每遍拿到的参数不同，操作的就是不同的硬件。

                                                  代码（一份）
                                                  probe / init / send ...
                                                  参数传入哪个文件夹，就操作哪个
                                                  文件夹 A
                                                  reg → A 寄存器 · cmdq → A 队列 · caps → A 能力
                                                  对应 IOMMU A 硬件
                                                  文件夹 B
                                                  reg → B 寄存器 · cmdq → B 队列 · caps → B 能力
                                                  对应 IOMMU B 硬件

                                                  代码怎么知道操作哪颗？看参数

                                                  int riscv_iommu_init(struct riscv_iommu_device *iommu)   // iommu 是参数
{
    riscv_iommu_queue_alloc(iommu, &iommu->cmdq, ...);   // 操作参数指向的那个
}

                                                  传 A 进来，iommu->cmdq 就是 A 的命令队列；传 B 就是 B 的。和 f(x)=x+1 一个道理：函数只有一份，x 传 3 得 4、传 5 得 6——函数不「知道」自己算的是哪个数，是调用者通过参数告诉它的。驱动所有函数都是这样，靠参数拿到具体的实例再操作。

                                                  共享什么、独立什么

                                                  独立（每颗 IOMMU 一份）共享（全局一份）
                                                  寄存器、命令队列、Fault 队列、设备目录表、能力值 capsriscv_iommu_ops 表、PSCID 分配器、blocking/identity 空 domain

                                                  共享的都是「无状态」的东西，多颗 IOMMU 共用不冲突；有状态的（寄存器/队列/目录）全是各管各的。内核 iommu core 只是「登记处 + 路由器」，登记所有 IOMMU、把设备路由到所属的那颗，并不替你操作硬件。

                                                  3.1 读写寄存器：relaxed 宏

                                                  驱动通过 iommu.h:71-89 的一组宏读写寄存器：

                                                  riscv_iommu_readl(iommu, addr)     // 读 32 bit 寄存器
riscv_iommu_readq(iommu, addr)     // 读 64 bit 寄存器
riscv_iommu_writel(iommu, addr, v) // 写 32 bit
riscv_iommu_writeq(iommu, addr, v) // 写 64 bit

                                                  它们展开成 readl_relaxed / writel_relaxed——relaxed 表示「不自动加内存屏障」。这意味着有顺序要求的操作（先写数据、再写门铃）必须由调用方显式加屏障。这个「屏障」是理解队列机制的关键，见下。

                                                  还有两个带超时的轮询宏，用来「等硬件完成某件事」：

                                                  riscv_iommu_readq_timeout(iommu, addr, val, cond, delay, timeout)
  // 反复读 addr 到 val，直到 cond 为真，或超过 timeout 微秒

                                                  3.2 队列怎么操作：无界 shadow 索引

                                                  这是驱动里最精巧的设计。队列是环形缓冲区，靠 Head/Tail 两个指针管理。但硬件寄存器里的 Head/Tail 是 32 位、会回绕的。软件直接维护会踩回绕的坑，所以想了个办法：

                                                  核心思想：软件用「无界整数」，硬件侧才取模

                                                  软件维护三个永远只增不减的 atomic_t（prod/head/tail），判断「队列满/空」就直接 tail - head 相减，永远不会因为回绕算错。只有在真正写硬件寄存器、或索引数组时，才用 Q_ITEM(index) = index & mask 取模（mask = 队列长度 - 1，是 2 的幂）。

                                                  队列结构（iommu.h:23-36）：

                                                  struct riscv_iommu_queue {
    atomic_t prod;   // 无界生产者索引
    atomic_t head;   // 无界 shadow 消费者索引
    atomic_t tail;   // 无界 shadow 生产者索引
    raw_spinlock_t lock;   // 序列化发布
    unsigned int mask;     // 队列长度 - 1（取模用）
    void *base;            // 环形缓冲区内核指针
    dma_addr_t phys;       // 物理地址
    u16 qbr;               // base 寄存器偏移
    u16 qcr;               // CSR 寄存器偏移
    u8 qid;                // 队列 ID
};

                                                  3.3 一条命令的入队过程（黄金例子）

                                                  riscv_iommu_queue_send（iommu.c:422-476）分四步，把「队列 + 屏障」讲透了：

                                                  // ① 等空间 + 占位
for (;;) {
    spin_lock(&queue->lock);
    prod = atomic_read(&queue->tail);
    head = atomic_read(&queue->head);
    if ((prod - head) < queue->mask)   // 无界相减判满
        break;
    spin_unlock(&queue->lock);
    riscv_iommu_queue_wait_for_space(...);  // 满了，等硬件消费
}

// ② 写数据到环形缓冲区
memcpy(queue->base + Q_ITEM(queue, prod) * entry_size, entry, entry_size);

// ③ 屏障后更新硬件 Tail（门铃）
dma_wmb();                                          // 数据先落地
riscv_iommu_writel(iommu, Q_TAIL(queue), Q_ITEM(queue, prod + 1)); // 再敲门铃

// ④ 门铃写完成，再更新 shadow tail
#ifdef CONFIG_MMIOWB
mmiowb();                                          // 等 MMIO 写完成
#endif
atomic_set(&queue->tail, prod + 1);
atomic_set(&queue->prod, prod + 1);
                                                  两个屏障，顺序不能反

                                                  dma_wmb()：保证「命令数据」先于「Tail 门铃写」被硬件看到——否则硬件一看到 Tail 前移，就去读还没写好的命令。mmiowb()：保证「门铃写」先于「shadow tail 更新」——否则别的 CPU 看到 shadow tail 已经 +1、以为命令发出去了，实际 MMIO 写还在路上。屏障是「保证顺序」的工具，不是「加速」的工具。

                                                  消费端（Fault 队列，iommu.c:312-339）：先看 shadow tail - head 有没有数据；没有就去读硬件 Tail 寄存器，把硬件新增的量加到 shadow tail 上；处理完 release 更新 head 并写硬件 Head 寄存器，告诉硬件「这些我读走了」。

                                                  3.4 发命令 + 等完成

                                                  riscv_iommu_cmd_send(iommu, &cmd)   // 入队一条命令，不等待
riscv_iommu_cmd_sync(iommu, timeout) // 发 IOFENCE.C 并等它执行完

                                                  cmd_sync 的机制：IOFENCE.C 命令带 PR|PW 位，硬件执行到它时保证「前面所有命令都已完成」。软件发完 fence 后轮询 Head 寄存器，等硬件消费过这条 fence，就说明前面的失效都生效了。fence 是「同步点」。

                                                  3.5 domain：软件侧的组织单位

                                                  软件把「一组页表 + 一个 PSCID」打包成一个 domain（iommu.c:836-845），多个设备可以共享一个 domain（共享同一套翻译）。

                                                  struct riscv_iommu_domain {
    union {
        struct iommu_domain domain;       // 内核框架视角
        struct pt_iommu_riscv_64 riscvpt; // 页表库视角
    };
    struct list_head bonds;   // 挂了哪些设备的链表
    spinlock_t lock;
    int pscid;                // 本 domain 的进程号
};

                                                  domain 和设备的关联用 bond 结构记录（iommu.c:871-875）。失效翻译时，遍历 bond 链表，对每个挂了这个 domain 的 IOMMU 各发一次失效命令。

                                                  4第四站：数据流 看懂全貌

                                                  把前三站的零件拼起来，跟着一个 DMA 请求走一遍

                                                  现在零件都认识了，把它们装成一条流水线。一个设备发起 DMA，从请求进来到翻译完成：

                                                  设备发 DMA
                                                  device id + IOVA + 读写属性
                                                  ① 用 device id 查 DDT
                                                  → 找到设备上下文 DC
                                                  ② 从 DC 取出页表指针和进程号
                                                  fsc（页表指针）· ta.PSCID（进程号）
                                                  ③ 用 IOVA 逐级查页表
                                                  每级 9 bit
                                                  查不到 → 写 Fault 队列 → 中断上报
                                                  ④ 得到物理地址 PA，上总线读写真实内存

                                                  4.1 device id 从哪来

                                                  PCIe 设备的 device id 就是 BDF（Bus:Device.Function）编码成一个数：device id = (Bus<<8) | (Device<<3) | Function。这是 IOMMU 在总线上天然能看到的，软件不用额外告知。

                                                  4.2 查 DDT：多级目录遍历

                                                  device id 被切成几段（DDI），每段作为一级索引逐级下钻。切分规则（iommu.c:606-625）分 base 和 extended 两种格式，取决于硬件是否支持 MSI_FLAT 能力。源码 riscv_iommu_get_dc（iommu.c:591）负责：校验范围 → 逐级下钻（没建的表当场分配）→ 定位叶子 DC。

                                                  4.3 页表翻译 IOVA → PA

                                                  从 DC 的 fsc 拿到页表根，用 IOVA 逐级翻译。SV39 为例：

                                                  VPN[2]
                                                  9 bit                                                   VPN[1]
                                                  9 bit                                                   VPN[0]
                                                  9 bit                                                   offset
                                                  12 bit
                                                  根页表
                                                  VPN[2] →
                                                  二级
                                                  VPN[1] →
                                                  三级
                                                  VPN[0] →
                                                  物理页
                                                  （叶子 PTE）
                                                  物理页号 + 12 bit offset = PA

                                                  非虚拟化场景只有一级翻译（IOVA→PA）。虚拟化场景两级翻译（IOVA→GPA→HPA），用 DC 里的 iohgatp 做第二级。本文聚焦前者。

                                                  4.4 翻译结果

                                                  成功 → 物理地址上总线。失败 → 硬件往 Fault 队列写一条记录并中断，cause 里常见 256（DMA 被禁）和 258（DDT 表项无效，即 DC.V=0）。

                                                  记住这条链，整份驱动都围绕它

                                                  device id → DC → 页表指针 + PSCID → IOVA 逐级翻译 → 物理地址。DDT 是「找 DC 的目录」，页表是「翻译的字典」，PSCID 是「缓存标签」，命令队列用来「维护缓存」，Fault 队列用来「报错」。一条链穿起来，驱动就没有秘密了。

                                                  5第五站：生命周期 串起来

                                                  驱动从开机到关机的完整历程，把前面所有零件串成时间线

                                                  启动
                                                  probe（接入层发现硬件）→ init（核心初始化）
                                                  设备接入
                                                  probe_device（预占位）→ attach（装页表）
                                                  运行时
                                                  unmap → iotlb_sync（失效）· fault（上报）
                                                  收尾
                                                  remove / shutdown

                                                  5.1 启动：probe → init

                                                  接入层发现硬件后调用核心 riscv_iommu_init（iommu.c:1580-1649），顺序有严格依赖：

                                                  ① QUEUE_INIT 配置命令队列、Fault 队列的寄存器偏移和默认长度
② init_check()  三项检查：DDTP 状态/kdump、字节序、中断向量
③ iodir_alloc() 分配 DDT 根页
④ queue_alloc(cmdq)  分配命令队列环形缓冲区
⑤ queue_alloc(fltq)  分配 Fault 队列
⑥ queue_enable(cmdq) 使能命令队列 + 注册中断
⑦ queue_enable(fltq)
⑧ iodir_set_mode(3LVL)  切 DDT 到多级模式
⑨ iommu_device_register(ops)  注册 ops，此后才接管设备
                                                  顺序里藏着一个强依赖

                                                  必须先使能命令队列（⑥⑦）再切 DDT 模式（⑧）。因为 iodir_set_mode 收尾要发 IODIR.INVAL_DDT + IOTINVAL.VMA + IOFENCE.C 三条命令去刷新硬件缓存，这些命令得靠已经使能的命令队列才能发出去。最后（⑨）才注册 ops——注册后 IOMMU 核心才会调 probe_device 接管设备，之前所有内部结构必须就绪。

                                                  启动里还有两个值得注意的细节：

                                                  • WARL 探测队列长度（queue_alloc，iommu.c:132）：软件写一个最大的 LOG2SZ 值，读回硬件实际支持的值，就能探测出队列能多长。这叫 WARL（Write Any, Read Legal）——硬件对任意写都返回一个合法值。
                                                  • WARL 探测 DDT 层级（iodir_set_mode，iommu.c:747）：从 3LVL 开始试，硬件不接受就降一级重试，直到成功或到 BARE/OFF。

                                                  5.2 设备接入：probe_device → attach

                                                  设备被接管时，core 调 probe_device（iommu.c:1452）。关键设计是「预占位但不启用」：给每个 device id 分配好 DC，但 tc = 0（V=0 无效）。此时设备发 DMA 会吃 fault（258）。

                                                  真正装页表在 attach_paging_domain（iommu.c:1305）：组装 fsc（页表根指针）和 ta（PSCID + V 位），建立 bond，然后调 iodir_update 更新 DC。

                                                  iodir_update 的两遍式更新（关键！）

                                                  riscv_iommu_iodir_update（iommu.c:1189-1249）分两遍，核心是V 位最后写：

                                                  // 第一遍：对每个已有效的 DC，先清 V，再失效缓存
for each id:
    if (dc->tc & TC_V) {
        WRITE_ONCE(dc->tc, tc & ~TC_V);   // ① 先摘 V（防设备用旧翻译）
        发 IODIR.INVAL_DDT + IOTINVAL;     // ② 失效缓存
    }

// 第二遍：写新配置，V 位最后点亮
for each id:
    WRITE_ONCE(dc->fsc, fsc);             // ③ 先写页表指针
    WRITE_ONCE(dc->ta, ta & PSCID);       // ④ 再写进程号
    dma_wmb();                            // ⑤ 屏障
    WRITE_ONCE(dc->tc, tc | V);           // ⑥ 最后写 V=1
    发 IODIR.INVAL_DDT + IOTINVAL;         // ⑦ 再失效缓存
                                                  为什么 V 位要最后写？

                                                  V 是「这个 DC 能不能用」的总开关。如果先写 V=1，硬件可能读到「新 V + 旧页表指针」的半新半旧状态，用错页表翻译。所以顺序必须是：先写数据字段 → 屏障 → 最后点亮 V。清的时候反过来：先摘 V → 失效缓存 → 再改数据。这是「先断电，再改线」的安全时序。

                                                  5.3 页表变更：unmap → IOTLB 失效

                                                  unmap 一块 IOVA 时，光删页表不够——硬件内部的 IOTLB（翻译缓存）还留着旧条目，必须显式失效（iotlb_sync → iotlb_inval，iommu.c:1051-1113）。

                                                  失效粒度决策 riscv_iommu_tlbi_calc（iommu.c:960-1003）是性能关键：

                                                  • 算出「能覆盖待失效区间的最小 NAPOT 范围」，一条命令搞定大块失效。
                                                  • 改的是非叶子页表、且硬件支持 NL 能力，才加 NL 位；否则只能全局失效（AV=0 全刷）。
                                                  • 地址太多（>512）就放弃逐条，改全局失效。

                                                  遍历 bond 链表，对每个不同的 IOMMU各发一次失效（一个 domain 可能挂多个 IOMMU）。链表按 IOMMU 分组，遍历时 if (iommu == prev) continue 去重。

                                                  5.4 故障处理

                                                  硬件写 Fault 队列 → 中断 → 中断线程 riscv_iommu_fltq_process（iommu.c:556）消费：读一批 → 逐个 riscv_iommu_fault 处理 → 释放空间。目前的 riscv_iommu_fault（iommu.c:542）只打印日志，还没实现真正的故障恢复（源码标注 placeholder）。中断用 threaded irq：硬中断只查状态，耗时处理放内核线程，不阻塞其他中断。

                                                  5.5 收尾：remove / shutdown

                                                  函数触发做什么释放资源吗
                                                  riscv_iommu_remove设备移除/驱动卸载注销 → 切 OFF → 关队列完整释放
                                                  riscv_iommu_disable关机/reboot/kexec切 BARE → 清队列 CSR不释放，仅停翻译

                                                  remove 顺序和 init 严格相反；disable 是「best effort」切 BARE 透传——马上断电了不回收内存，但必须停掉翻译，防关机时设备还在发 DMA 打到半关闭的页表。

                                                  6第六站：两个接入层 收尾

                                                  同一颗 IOMMU 硬件，可挂 PCIe 总线，也可作平台设备

                                                  核心 iommu.c 与总线无关，真正接到系统上靠两个薄薄的接入层。它们各自「发现硬件 + 配置中断」，然后都调用同一个 riscv_iommu_init。

                                                  6.1 PCIe 接入（iommu-pci.c）

                                                  pcim_enable_device(pdev)                  // 托管式使能设备
校验 BAR0 是 MEM 型且 ≥ 0x1000             // 寄存器区至少 4KB
pcim_iomap_regions(pdev, BIT(0), ...)      // ioremap BAR0
读 caps / fctl
校验 IGS 支持 MSI（MSI 或 BOTH）           // PCI 只用 MSI
pci_alloc_irq_vectors(1..4, MSIX|MSI)      // 分配 MSI/MSI-X
逐向量 msi_get_virq 填 irqs[]
清 fctl.WSI（若置位）
return riscv_iommu_init(iommu)             // 交给核心

                                                  要点：PCIe 设备的 MSI 是标准 capability，内核 PCI 层自动处理，驱动只管分配向量、取 virq。

                                                  6.2 平台接入（iommu-platform.c）

                                                  差别全在中断，按 IGS 分三路（iommu-platform.c:73-140）：

                                                  • MSI 路：平台设备没有 PCI 的 MSI capability，要用规范定义的内部 MSI 配置表（0x0300）。驱动自己实现 riscv_iommu_write_msi_msg（iommu-platform.c:24-44），把「地址+数据」写进表，硬件发中断时按表发消息。
                                                  • WSI 路：传统线中断，4 类事件各占一根线，platform_get_irq 解析，置位 fctl.WSI。
                                                  • 降级：MSI 配失败但 IGS=BOTH 时，fallthrough 降级到 WSI。

                                                  6.3 对比

                                                  维度PCIe平台
                                                  寄存器映射读 BAR0读第 0 个 MEM 资源
                                                  中断模式只用 MSI/MSI-XMSI + WSI 双模式
                                                  MSI 消息写入内核代劳软件写内部 MSI 配置表
                                                  匹配方式vendor/device IDcompatible（OF）+ _HID（ACPI）
                                                  两个接入层一句话

                                                  PCIe 的 MSI 是标准 capability，内核自动处理；平台设备的 MSI 没有标准结构，RISC-V IOMMU 规范定义了内部 MSI 配置表，驱动要自己写 write_msi_msg 回调。这是最本质的区别。
