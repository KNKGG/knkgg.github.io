                                      RISC-V IOMMU 页表 · 学习攻略

                                      第一级 / 第二级翻译 · DMA 路径 vs 直通路径 · 两条源码阅读路线
                                      源码 drivers/iommu/ · drivers/iommu/riscv/ · arch/riscv/kvm/ · drivers/vfio/ · 对照 RISC-V IOMMU Architecture Specification（riscv-iommu zh.md）

                                      1第一站：心智模型 不碰代码

                                      先把「页表在 IOMMU 里到底干什么」这件事钉死，后面所有代码都是在实现这个模型。

                                      1.1 页表的唯一任务：把 IOVA 翻译成物理地址

                                      IOMMU 是「给设备用的 MMU」。设备发起 DMA 时，地址线上出现的是 IOVA（I/O 虚拟地址），不是真实物理地址。IOMMU 用页表把 IOVA 翻译成真正的物理地址，并检查权限。这个页表和 CPU 的页表一样，是多级结构（Sv39 三级 / Sv48 四级 / Sv57 五级，每级 9 bit 索引）。

                                      1.2 三种地址，先分清楚

                                      缩写全称是谁的视角举例
                                      VA / IOVAI/O Virtual Address设备发出来的虚拟地址驱动给设备编程的缓冲区地址
                                      GPAGuest Physical AddressGuest OS 眼里的「物理地址」（其实还是虚拟的）guest 驱动认为的物理地址
                                      SPASupervisor Physical Address真实物理内存地址（host 的）内存控制器真正用的地址

                                      1.3 两级翻译：第一级（VS 级）+ 第二级（G 级）

                                      IOMMU 支持两阶段地址转换（规范 zh.md:230-233），刻意和 CPU MMU 用同一套页表格式：

                                      IOVA
                                      设备 DMA 地址
                                      第一级（VS 级）
                                      iosatp · Guest OS 建
                                      VA → GPA
                                      GPA
                                      第二级（G 级）
                                      iohgatp · Hypervisor 建
                                      GPA → SPA
                                      SPA
                                      真实物理地址

                                      两级各有一个「主人」：第一级（VS 级）由 Guest OS 用 iosatp 控制；第二级（G 级）由 Hypervisor 用 iohgatp 控制。名字直接对应 CPU 侧：vsatp → iosatp、hgatp → iohgatp，只加了个 io 前缀。

                                      1.4 四种配置：哪一级开、哪一级关

                                      规范 zh.md:237-250 用「某一级是不是 Bare（关闭）」分出四种情况，这是理解一切的钥匙：

                                      第一级（VS）第二级（G）IOVA 被当作翻译链对应场景
                                      BareBareSPA不翻译设备直连物理地址
                                      Bare启用GPAGPA → SPA直通，guest 不自己限制
                                      启用BareVAVA → SPAhost 自用 / 非虚拟化
                                      启用启用VAVA → GPA → SPA直通，guest 自己也限制
                                      最容易踩的坑：判断「哪一级」看输入，不看输出

                                      「翻译结果是不是物理地址」不能用来判断是第几级。要看输入：收 VA 的是第一级（VS 级），收 GPA 的才是第二级（G 级）。所以「VA → SPA」是第一级在第二级 Bare 时的单级行为（类似 CPU 非虚拟化的 satp 单级翻译），不是 G 级干的活——G 级从来不碰 VA，它只收 GPA。

                                      2第二站：谁创建哪一级页表 责任分工

                                      页表不是凭空出现的，每级都有明确的「作者」。搞清楚作者，才知道去哪个目录找代码。

                                      2.1 先破除一个误解：Host OS 和 Hypervisor 是一体的

                                      在 Linux/KVM 架构下，KVM（Hypervisor）就是 Linux 内核里的一个模块，不是独立于 Host OS 之外的程序。所以「Hypervisor 创建第二级页表」这句话，翻译成实现就是 「Host OS 内核里的 KVM 模块创建第二级页表」。Host OS 不是「没活干」，它恰恰是建第二级页表的人，还是整个 IOMMU 硬件的「主人」。

                                      2.2 三层分工

                                      角色创建/管理什么对应代码
                                      Host OS（内核，含 KVM）① IOMMU 一切数据结构：DDT、DC、MSI 页表
                                      ② host 自己设备的第一级页表
                                      ③ 通过 KVM 建 guest 直通设备的第二级页表                                      		drivers/iommu/ + arch/riscv/kvm/
                                      Hypervisor（KVM）guest 直通设备的第二级页表（G 级）arch/riscv/kvm/gstage.c
                                      Guest OS只建「它自己直通设备」的第一级页表，且是 hypervisor 授权它建的guest 内核里（host 侧不建）

                                      2.3 用规范原文的三个设备把场景钉死

                                      规范 zh.md:505-518 用 D1/D2/D3 三个设备讲清「谁用设备 → 哪级启用」：

                                      设备谁在用第一级第二级说明
                                      D3host / Hypervisor 自用启用Bare非虚拟化，第一级就够（zh.md:517-518）
                                      D2直通给 VMBare启用直通，guest 不自己限制（zh.md:516）
                                      D1直通给 VM启用启用直通，guest 也限制（zh.md:513-515）

                                      规律很干净：只要设备被直通给 VM，第二级就必然启用（D1/D2）；只要设备 host 自用，第二级就 Bare（D3）。所以「第二级启不启用」=「直通 vs 软件虚拟化」的分水岭。

                                      类比：房东 / 物业 / 租客

                                      Host OS = 房东（拥有整栋楼 + 一切门锁）；KVM = 房东兼任的物业（就是房东的内核模块）；Guest OS = 租客。

                                      第二级页表 = 房东/物业登记的「楼宇真实房号表」（房东建）；第一级页表 = 租客在自己房间里贴的「房间内部布局图」（租客建，但房间是房东的，布局图也是房东允许你贴的）。

                                      3第三站：两条阅读路线总览 地图

                                      学「页表创建」分两条线。这一站先把地图摊开，后面两站逐条走。

                                      线 1：第一级页表（host 自用，DMA 路径）
                                      dma-iommu.c（DMA API 入口）→ iommu.c（IOMMU core）→ io-pgtable.c（通用页表 walk）→ drivers/iommu/riscv/iommu.c（RISC-V 具体实现）
                                      不碰 KVM，不碰虚拟化
                                      线 2：第二级页表（guest 直通，G 级）
                                      drivers/vfio/（设备 bind 到 guest domain）→ iommu.c（domain attach）→ arch/riscv/kvm/gstage.c + mmu.c（第二级页表 G-stage + KVM MMU）
                                      需要 KVM + VFIO
                                      线 1（第一级）线 2（第二级）
                                      翻译什么VA / IOVA → SPAGPA → SPA
                                      谁建的Host OS（DMA 路径）KVM（guest 直通）
                                      要不要学 KVM不要要
                                      要不要学 VFIO不要要
                                      前置知识无（纯 IOMMU/DMA）线 1 的页表 walk 机制
                                      建议顺序：先线 1，再线 2

                                      线 1 是「一个物理设备 + 一份页表」的最干净场景，先把页表 walk 机制吃透（PTE 怎么分配、几级页表、怎么失效）。线 2 的 gstage.c 用的是同一套页表格式（Sv39/Sv48，只是 hgatp 指向），学完线 1 再看会快很多——线 2 新增的主要是「KVM 怎么把 guest 的 GPA 空间和 IOMMU domain 绑起来」这层胶水。

                                      4第四站：线 1 详解 — 第一级页表（DMA 路径）不碰 KVM

                                      这条线回答：host 自己的设备，DMA 用的页表是谁建的、怎么建、怎么 walk。

                                      4.1 dma-iommu.c — DMA API 到 IOMMU 的桥（入口）

                                      设备驱动申请 DMA 缓冲区时，最终会进到这里。关键入口：

                                      • iommu_dma_alloc_iova()（dma-iommu.c:760）— 从 IOVA 空间分一段连续地址。
                                      • iommu_dma_alloc_pages()（dma-iommu.c:1621）— 分物理页 + 建立「IOVA → 物理页」映射。

                                      抓什么：看懂「驱动要一段 DMA 内存」是怎么变成「一段 IOVA + 一份页表映射」的。这是第一级页表创建的触发源头。

                                      4.2 iommu.c — IOMMU core（抽象层）

                                      不关心具体硬件，只提供统一接口：domain（一组页表）、attach_dev（把设备绑到 domain）、map / unmap（建/拆映射）。

                                      抓什么：理解 domain 这个核心概念——它是一份页表 + 一个编号，可被多个设备共享。所有「建页表」的操作最终都落到某个 domain 上。

                                      4.3 io-pgtable.c — 通用页表 walk（核心）

                                      这是「页表创建」的真身。它提供一套与具体硬件无关的页表操作：

                                      • alloc_io_pgtable_ops()（io-pgtable.c:53）— 按页表格式（如 RISC-V 的 Sv39/Sv48）分配一套操作。
                                      • struct io_pgtable_ops — 里面是 map / unmap / iova_to_phys 等函数指针。

                                      抓什么：这是最重要的一个文件。看懂 PTE 怎么分配、多级页表怎么逐级下钻（walk）、叶子 PTE 怎么填物理页号、失效时怎么清。RISC-V 驱动不手写页表，复用的就是这套通用库。

                                      4.4 drivers/iommu/riscv/iommu.c — RISC-V 具体实现

                                      把通用层接到 RISC-V 硬件上。关键符号：

                                      • riscv_iommu_ops（riscv/iommu.c:1506）— 驱动的总 ops 表。
                                      • .domain_alloc_paging = riscv_iommu_alloc_paging_domain（:1511）— 建 paging domain 时，决定用 Sv39/Sv48。
                                      • .attach_dev = riscv_iommu_attach_paging_domain（:1337）— 把设备挂到 domain，写 DC。
                                      • .iotlb_sync = riscv_iommu_iotlb_sync（:1339）— 失效 IOTLB。

                                      抓什么：看懂「通用页表 + RISC-V 寄存器」怎么合体——domain 建好后，驱动把页表根写进 DC 的 fsc（第一级页表指针，对应 iosatp），再写 tc.V 使能翻译。这是「页表真正生效」的那一步。

                                      线 1 的阅读顺序

                                      dma-iommu.c（入口）→ iommu.c（domain 概念）→ io-pgtable.c（页表 walk，重点）→ riscv/iommu.c（落到寄存器）。这条线走完，你就懂了「host 设备的第一级页表」的完整生命周期。

                                      5第五站：线 2 详解 — 第二级页表（直通路径）需要 KVM + VFIO

                                      这条线回答：设备直通给 guest 时，第二级页表（G 级，GPA→SPA）是谁建的、怎么和 guest 地址空间绑起来。

                                      5.1 drivers/vfio/ — 把设备「交出去」给 guest

                                      VFIO 是「设备直通给用户态 / VM」的框架。它负责把设备从 host 驱动手里接管，绑到一个 IOMMU domain 上。关键文件：

                                      • vfio_main.c — VFIO 核心，设备生命周期。
                                      • iommufd.c / vfio_iommu_type1.c — 两种 IOMMU 后端，管理「设备 → domain → 页表」的绑定。
                                      • pci/vfio_pci_core.c — PCI 设备直通的核心逻辑。
                                      • group.c — IOMMU group（我们之前讲的「隔离最小粒度」）。

                                      抓什么：看懂「一个物理设备怎么被划进 IOMMU group、怎么绑到某个 domain、domain 的页表怎么对应到 guest 的地址空间」。这层是「胶水」。

                                      5.2 arch/riscv/kvm/gstage.c — 第二级页表的真身

                                      这是第二级页表（G 级）的实现。铁证在代码里：它操作的是 gpa_t addr（guest 物理地址）和 HGATP_PAGE_SHIFT（hgatp 就是第二级页表寄存器），函数名直接叫 kvm_riscv_gstage_get_leaf（walk 第二级页表找叶子 PTE）。gstage = G-stage = G 级 = 第二级。

                                      抓什么：第二级页表的 walk、PTE 填充（把 guest 的 GPA 映射到 host 的物理页）、以及和 hgatp 的关系。注意它用的页表格式和线 1 的 io-pgtable.c 是同一套 Sv39/Sv48，只是 root 由 hgatp 指、输入是 GPA。

                                      5.3 arch/riscv/kvm/mmu.c — KVM 的 MMU 管理

                                      KVM 的地址空间管理：guest 内存、缺页处理、页表失效（配合 tlb.c、vmid.c）。

                                      抓什么：KVM 怎么维护「guest 的 GPA 空间」，以及它和 IOMMU 第二级页表如何保持映射一致（CPU 的 EPT 和 IOMMU 的第二级，语义上是对齐的）。

                                      线 2 的阅读顺序

                                      vfio_main.c + iommufd.c（设备怎么交出去）→ gstage.c（第二级页表 walk，重点）→ mmu.c（KVM 地址空间管理）。这条线走完，你就懂了「guest 直通设备时，第二级页表从无到有、到被设备 DMA 使用」的全过程。

                                      6.3 三个反复强调的坑

                                      • 判断第几级看输入不看输出：收 VA 是第一级，收 GPA 才是第二级。
                                      • Host OS 和 KVM 是一体：「Hypervisor 建第二级」=「Host OS 内核的 KVM 模块建第二级」，Host OS 不是旁观者。
                                      • 软件虚拟化场景的真实设备 = D3：它只有第一级（VA→SPA），第二级 Bare；那层 GPA→SPA 的「隐藏翻译」跑到了 CPU 的 EPT/NPT 里，跟 IOMMU 无关。
                                      最后一句

                                      学页表不要一上来啃 KVM。先把 host 自用的第一级页表（dma-iommu → io-pgtable → riscv/iommu）吃透，再带着这套页表知识去看 KVM 的 gstage.c（第二级）——两者是同一套 Sv39/Sv48 格式，只是「谁建、翻译哪段地址」不同。
