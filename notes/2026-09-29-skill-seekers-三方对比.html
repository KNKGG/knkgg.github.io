                            skill-seekers 家族：三方定位 + SystemVerilog/UVM 识别原理

                            同一个名字底下的三个工具——全功能旗舰 skill-seekers、精简 fork simple-skill-seekers、自建 SV/UVM 补丁 svcode-skill-seekers；以及 tree-sitter 是怎么「读懂」class、extends 和 uvm_component 的
                            来源：skill-seekers v3.9.1（pip 包）· simple-skill-seekers v0.1.0（无 AI 增强 fork）· svcode-skill-seekers v0.2.0（自建，源码在 ~/svcode-skill-seekers/）· 解析器 tree-sitter-systemverilog · 信息截至 2026-09

                            1为什么会有三个「skill-seekers」动机

                            同一个名字底下，其实是三条不同的路：全功能、做减法、补语言

                            skill-seekers 是把「现成资料」自动变成 Claude Skill 的工具：给它 PDF、文档网站、GitHub 仓库或本地代码，它提取内容、生成 SKILL.md + 结构化参考文件，还能 AI 增强、一键装到 ~/.claude/skills/。它追求的是「覆盖一切资料源 + 一切 AI 平台」。

                            在这条主线上，另外两个工具从不同方向切了出去：

                            • simple-skill-seekers：从 skill-seekers fork 出来，砍掉 AI 增强，只留「把资料变成 skill」的确定性核心——方向是「做减法」。
                            • svcode-skill-seekers：完全自建，只解决一件事——skill-seekers 原生不认 SystemVerilog / UVM，它用 tree-sitter 补上这块语言空白——方向是「做加法」。
                            先澄清一个常见误解

                            svcode-skill-seekers 不是 skill-seekers 的「加强版 / 完整版 + SV 支持」。它只做一件事——把 SV/UVM 源码解析成 Skill，只有 create、install、update 三个命令，从 skill-seekers 那里复用了渲染和安装两个模块。三者是「各管一段」，不是包含关系。

                            一句话定位

                            skill-seekers：全能选手，多源（18 种）+ 多语言 + 20 多个命令 + AI 增强。

                            simple-skill-seekers：做减法的精简 fork——去 AI、去外围，只留 6 种源的确定性转换。

                            svcode-skill-seekers：专精一件小事——只吃 SV/UVM 源码，吐出同款 Skill，只有三个命令。

                            3simple-skill-seekers：把「AI 增强」抽掉 理念

                            做减法——证明「把资料变成 skill」这件事，AI 不是必需品

                            simple-skill-seekers 是 skill-seekers 的一个 fork，理念只有一条：「把资料变成 skill」这件事，AI 增强是可选件，不是必需品。

                            原版 skill-seekers 的完整形态，可以拆成三块：

                            1. 确定性转换主线——提取 → 结构化 → 渲染成 SKILL.md + 参考文件；
                            2. AI 增强副线——enhance、scan 等命令，依赖 anthropic / langchain / llama-index；
                            3. 外围子系统——多平台打包/上传、MCP、同步、embedding 等。

                            但如果你只需要第一块——把一个 PDF、一个 HTML 页面、或一个代码库变成结构化的 skill——这整条主线是纯文本处理，不调用任何 LLM 也能完成。所以 simple-skill-seekers 做的事是「减法」：

                            • 砍掉 AI 增强整条线，以及多平台打包/上传等外围；
                            • 只留 6 种源：C/Python 代码、PDF、HTML、Word、PPTX；
                            • 命令瘦身到 create / detect / doctor 三个；
                            • 核心依赖从 22 个降到 18 个。

                            换来的是：更轻、依赖更少、行为完全确定（同样的输入永远同样的输出）、不依赖任何外部服务。它的存在回答了这样一个问题——如果你根本用不上 AI 增强，为什么还要为它背上几十个依赖？

                            三个工具的关系

                            如果 skill-seekers 是「全能旗舰」，simple-skill-seekers 就是「精简版」（砍掉你不用的），svcode-skill-seekers 则是「外挂补丁」（补上它没有的）。三者不是竞争关系，而是同一个问题——「怎么把资料变成 skill」——的三个不同答案。

                            4svcode-skill-seekers 架构：5 个模块各司其职 架构

                            svcode-skill-seekers 内部的数据流从上到下，最后落到 skill-seekers 兼容的产物结构

                            SV/UVM 源码目录
                            .sv / .svh / .svp / .svi
                            systemverilog.py
                            tree-sitter 真实 AST 解析 → classes / functions / comments
                            scraper.py
                            遍历目录、过滤文件 → code_analysis.json
                            api_reference.py + skill_builder.py
                            生成 references/api_reference/*.md + SKILL.md
                            cli.py
                            create <dir> 串起全流程 · update <dir> 增量刷新 · install <skill_dir> 装到各 AI agent

                            4.1 模块职责一览

                            模块行数职责
                            systemverilog.py301核心：用 tree-sitter 解析 SV，提取 class（含 extends）、方法、方法签名（参数/返回类型）、doc 注释
                            scraper.py149遍历目录，识别 SV 扩展名，做前缀/目录/文件名过滤，产出 {"files": [...]}；增量模式按内容 sha256 对比、只重析变化文件
                            api_reference.py373拷贝自 skill-seekers（MIT），把分析结果渲染成 markdown API 文档
                            skill_builder.py115拼出 SKILL.md（frontmatter + 统计 + 引用指引）
                            cli.py239命令行入口，分发 create / update / install 三个子命令
                            install_agent.py331拷贝自 skill-seekers（MIT），把生成的 skill 目录拷贝到各 AI agent 的 skills 目录

                            注意 api_reference.py 和 install_agent.py 的特殊身份——它们都是从 skill-seekers 原样拷贝过来的（MIT，文件头保留版权声明），这样下游「渲染 markdown」和「安装到 agent」这两步就能直接复用，不用自己重写（详见第 7 节）。

                            5接入 SystemVerilog：tree-sitter 真实 AST 核心

                            整个工具的命门在 systemverilog.py 的前 20 行

                            5.1 为什么不用正则

                            解析「哪些是 class、谁继承谁、方法归属哪个类」，最容易想到的是正则 + 括号匹配。但 SV 语法太灵活——virtual function、extern 声明、pure virtual、宏包裹、注释里的假代码……正则很快会漏匹配或误匹配，而且维护不下去。

                            正确姿势是交给一个真正的语法解析器。这里选的是 tree-sitter：一个增量解析框架，配上一份 SV 的 grammar（tree-sitter-systemverilog），就能把源码变成一棵 语法树（AST）——每个 class、function、extends 都是树上一个有类型的节点，而不是一段要靠正则猜的文本。

                            5.2 三行接入 grammar

                            接入 tree-sitter-systemverilog 只用了三行：

                            import tree_sitter_systemverilog as tssv
from tree_sitter import Language, Parser

_PARSER = Parser(Language(tssv.language()))   # 拿到 SV 的 grammar，构建解析器

                            tssv.language() 返回 tree-sitter 的 Language 对象（SV 语法规则），塞进 Parser 就得到一个能解析 SV 源码的解析器。之后对任意 SV 文本调 _PARSER.parse(source).root_node，就得到整棵语法树的根节点，再递归遍历即可。

                            5.3 识别 class / extends / 方法

                            核心是一个递归 walk：从根节点往下，遇到特定 节点类型 就做对应提取。关键是这张类型清单——它把「SV 里什么算方法」写全了：

                            _METHOD_TYPES = (
    "function_declaration",   # function 实现
    "task_declaration",        # task 实现
    "function_prototype",      # extern function 声明
    "task_prototype",           # extern task 声明
    "class_constructor_declaration",  # new()
    "class_constructor_prototype",
)

                            遍历时：

                            • 遇到 class_declaration → 建一个 class 记录，提取名字、行号；
                            • class 里有 class_type 子节点 → 那就是 extends 父类，提取父类名存进 base_classes；
                            • 遇到上面那些方法类型 → 提取方法名，挂到当前 class 的 methods 里；
                            • 构造函数特殊处理，统一命名成 new。

                            提取父类的关键函数长这样——沿着 class_type → simple_identifier 取到标识符文本：

                            def _class_base(node, source):
    ct = _direct_child(node, "class_type")
    n = _direct_child(ct, "simple_identifier")
    return source[n.start_byte : n.end_byte].decode()
                            为什么用节点类型而不是文本匹配

                            正则看到的是「一串字符」，tree-sitter 看到的是「一个 class_declaration 节点，下面挂着一个 class_type 子节点」。后者天生带着语法结构，extends 关系、方法归属、注释位置都变成了树的父子关系，提取只是「按类型找子节点」，不用猜。

                            5.4 doc 注释怎么挂对位置

                            方法/类的 docstring 来自源码里 /** ... */ 形式的注释。难点是「怎么确定这个注释属于下面哪个声明」——尤其 SV 里注释和声明之间可能隔着 extern、virtual、static 这些修饰符。

                            做法：先扫出所有 /** ... */ 注释（记录结束位置），对每个声明找「结束位置最靠近、且中间只隔修饰符/空白」的那条注释。中间的修饰符白名单长这样：

                            _MODIFIERS_RE = re.compile(
    r"^(?:\s*(?:extern|virtual|static|pure|local|protected|public|rand|randc|const|automatic))*\s*$"
)

                            这样 /** doc */ virtual function f(); 里的注释也能正确挂到 f 上，而不是因为中间有个 virtual 就丢了。

                            6识别 UVM：本质是 class + extends 核心

                            UVM 没有单独的 grammar，因为它本来就是 SV

                            这是最容易误解的一点：svcode-skill-seekers 并没有「UVM 解析器」。UVM 里的 uvm_object、uvm_component、uvm_sequence、uvm_driver、uvm_monitor……统统都是 SystemVerilog 的 class。

                            验证工程师写的 UVM 代码，本质就是「定义一堆 class，并用 extends 表达它们之间的继承关系」：

                            /** AXI slave agent: 驱动接口的 slave 侧 */
class axi_slave_agent extends uvm_component;

  /** 构建 driver 和 monitor */
  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
  endfunction

  /** 返回 slave driver 句柄 */
  virtual function axi_slave_driver get_driver();
    return driver;
  endfunction

endclass

                            对这段代码，前面的解析逻辑会自然产出：一个 class axi_slave_agent，base_classes = ["uvm_component"]，两个方法 build_phase、get_driver，各自挂着 doc 注释。

                            换句话说：「识别 UVM」=「识别 SV class」+「提取 extends 的父类」。只要把 extends 关系抓准，UVM 的组件层次（谁继承 uvm_component、谁继承 uvm_sequence、driver 继承哪个 base）就自动浮现了，根本不需要为 UVM 单独写一套规则。

                            这也解释了为什么用 tree-sitter 就够

                            UVM 不是一种新语言，是 SV 之上的一套库 + 约定。所以一份 SV 的 grammar 就同时覆盖了「普通 SV」和「UVM」，svcode-skill-seekers 才能用最小的改动补上这个空白。

                            7与 skill-seekers 的「缝合」 设计

                            两条线对齐，让下游能复用，而不是另起炉灶

                            7.1 输出 shape 对齐

                            skill-seekers 分析 C/C++ 后产出的结构是 {"classes": [...], "functions": [...], "comments": [...]}。svcode-skill-seekers 的 systemverilog.py 也输出一模一样的 shape：

                            {
  "classes": [
    {"name", "base_classes", "methods", "docstring", "line_number"}
  ],
  "functions": [...],
  "comments": [...]
}

                            这个对齐是刻意的：只要解析结果长一个样，后面「渲染成 markdown、打包成 skill」的下游工具就不用改一行，直接消费。

                            7.2 拷贝复用 APIReferenceBuilder

                            下游那一段（把 classes/functions 渲染成 references/api_reference/*.md）干脆直接从 skill-seekers 原样拷贝了 APIReferenceBuilder（MIT 协议，文件头保留了版权声明）。

                            这样做的取舍很清晰：

                            • 省：markdown 渲染（签名、参数表、继承标注）是纯格式活，跟语言无关，没必要重写；
                            • 独立：拷贝而非 import skill_seekers，保证 svcode-skill-seekers 零 skill-seekers 运行时依赖，装起来只要 tree-sitter 两个包。

                            所以准确说，svcode-skill-seekers 的「原创」只有 systemverilog.py（SV AST 解析）和 scraper.py（遍历过滤），其余是「复用 skill-seekers 的两个下游模块（渲染 + 安装）+ 一个薄薄的 cli.py」。这是一次典型的「缝合」而非「重造」。

                            有意思的是，simple-skill-seekers 也是「从 skill-seekers 出发」——但它走的是另一条路：直接 fork 整棵代码树，保留整条转换主线、砍掉 AI 和外围（删），而不是像 svcode 这样「只挑两个下游模块来复用」（取）。删和取，殊途同归，都证明了 skill-seekers 是「可拆分」的——它的核心转换能力和它的 AI 增强、多平台能力，本来就是解耦的两层。

                            8实战与诚实的边界 落地

                            跑通了一个真实目录，补上了方法签名和增量更新

                            8.1 给 axi_vip 生成方法级 API

                            拿某个 AMBA 验证 IP（VIP）的 AXI 部分跑了一遍，用过滤参数只抓 axi_ 前缀、去掉 com/mti/ncv 仿真器变体和 .ovm./.vmm. 方法学变体：

                            svcode-skill-seekers create <某 AMBA VIP 目录> \
  --filter axi_ \
  --exclude-dir com --exclude-dir mti --exclude-dir ncv \
  --exclude-name .ovm. --exclude-name .vmm.

                            结果：177 文件 → 417 类 → 4260 方法，生成的方法级 API 文档直接喂给了 axi_vip 这个 skill 的 references/api_reference/，让 Claude 能按需查到「某个 class 继承谁、某方法干嘛的」。

                            生成完 skill，还能用 install 命令一键装到各 AI coding agent 的 skills 目录：

                            svcode-skill-seekers install output --agent claude        # 拷到 ~/.claude/skills/
svcode-skill-seekers install output --agent all --dry-run  # 预览装到全部 agent

                            8.2 补上方法签名：return_type + parameters

                            初版只提取「类 + 继承 + 方法名 + docstring + 行号」，方法 dict 里的 parameters 和 return_type 是空占位。后来补上了这两个字段——同样从 tree-sitter 的 AST 里取，没引入任何新依赖：

                            def _return_type(node, source):
    # 沿 function/task_body_declaration → data_type_or_void 取返回类型文本
    ...

def _params(node, source):
    # 遍历 tf_port_list → tf_port_item，取参数名 + 方向/类型/维度拼成 type_hint
    params.append({"name": name, "type_hint": "...", "default": None})

                            现在产出的方法记录带上了完整签名——parameters（参数名 + 类型标注）和 return_type（返回类型）都不再是空占位。顺带还支持了 // Function: / // Task: 这种行注释形式的 docstring，让只有行注释、没有块注释的方法也能挂上说明；注释里的签名行会被识别并跳过（避免和 AST 提取的 return_type/params 重复）。

                            8.3 增量更新：update 命令

                            验证项目更新频率高时，每次 create 全量重析几百个文件没必要。于是加了 update 命令——把上次的 code_analysis.json 当快照，按文件内容 sha256 对比：变化/新增的文件才重新解析，已移除文件的 .md 删掉，未变化的直接复用：

                            svcode-skill-seekers update <目录> -o output   # 参数与 create 完全一致

                            实测（144 文件的 UVM 源码）：全量 create 约 1.9s，改 1 个文件的 update 约 0.16s，约 12 倍提速。没有历史快照时会自动回退全量。

                            一句话总结

                            skill-seekers 家族的三条路——全功能（原版）、做减法（simple-skill-seekers：去 AI 留确定性转换）、补语言（svcode-skill-seekers：用 tree-sitter 把 SV/UVM 源码变成真实语法树，再对齐 skill-seekers 的输出 shape 复用下游渲染）。三者合起来，回答的是同一个问题：怎么把不同形态的资料，变成 Claude 能直接用的 skill。
