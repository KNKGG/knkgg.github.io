          fsdb2fst 离线安装

          让 wave-mcp 吃上 FSDB——不靠 pip/git 更新，在有 Verdi 的隔离机上把 fsdb2fst 编出来
          来源：Tencent/wave-mcp · docs/FSDB_GUIDE.md · deploy/build_fsdb2fst.sh · 信息截至 2026-10-22

          1背景：为什么要单独装 原理

          先搞清 fsdb2fst 是什么、为什么它不在 wave-mcp 的包里

          wave-mcp 原生用 fsdb2fst 做 FSDB → FST 直转。相比「fsdb → vcd → fst」的中转路线，直转不损失 real 信号的精度、时间刻度原样透传，且省掉 VCD 文本的体积爆炸。

          但它不是随仓库 / PyPI 分发的东西，原因有二：

          • 编译时必须 link Verdi 的 proprietary 库 libnffr.so + libnsys.so，这两库永不进仓库 / 包，只能本地链接。
          • 所以它是个「本地产物」，在有 Verdi 库的 Linux 机器上按需编译，产物进用户缓存目录。
          「找不到 fsdb2fst」的典型根因

          老 pip 包（< 0.2.6）连源码都没打进去（share/wave-mcp/fsdb2fst/ 缺失），自动编译无料可编，于是报 converter sources are not shipped in the PyPI package。这套流程在不重装的前提下手动补齐。

          wave-mcp 查找 fsdb2fst 的顺序：$FSDB2FST_BIN → 仓库本地 → 用户缓存 → PATH → 按需自动编译。只要把 $FSDB2FST_BIN 指向编好的二进制，就能绕过后面所有环节。

          2机器拓扑与方案 选型

          三台机器的能力不同，方案要顺着「谁有 Verdi、谁能上网」走

          机器有网有 Verdig++角色
          Mac（操作机）✅❌—指挥 / 中转
          联网机✅❌—下载源码、打包
          隔离机❌✅9.5.0编译 + 运行
          关键决策：在隔离机本地编，而不是联网机编好拷二进制

          联网机没 Verdi 编不了；即便从隔离机把库拷过去编，也会踩 glibc 版本坑（新 glibc 编的二进制在旧机器上 GLIBC_xx not found）。隔离机本地编：Verdi 本地有、glibc / 架构天然匹配、拷的只是 113K 源码包。

          3完整安装流程（7 步） 实操

          第 1 步在联网机，第 2–7 步在隔离机

          ① 联网机：下载并打包源码

          curl -fL https://github.com/Tencent/wave-mcp/archive/refs/heads/main.tar.gz -o /tmp/wave-mcp.tar.gz
tar xzf /tmp/wave-mcp.tar.gz -C /tmp
cd /tmp/wave-mcp-main
tar czf /tmp/fsdb2fst-src.tar.gz third_party/fsdb2fst deploy/build_fsdb2fst.sh

          验证（缺一不可，约 113K）：

          ls -lh /tmp/fsdb2fst-src.tar.gz
tar tzf /tmp/fsdb2fst-src.tar.gz | grep -E 'fsdb2fst.cpp$|build_fsdb2fst.sh$|fstapi.c$'

          ② 传输到隔离机

          scp /tmp/fsdb2fst-src.tar.gz <隔离机主机名>:/tmp/

          ③ 隔离机：前置核对

          which g++ && g++ --version | head -1        # 需 ≥ 7（C++17）
ls -d "$VERDI_HOME/share/FsdbReader/linux64/libnffr.so"

          若环境变量不叫 VERDI_HOME（公司自定义），改设 FSDB2FST_FREADER=/path/to/FsdbReader，效果相同。库解析顺序：FSDB2FST_FREADER → VERDI_HOME → NOVAS_HOME。

          ④ 隔离机：编译

          cd /tmp && tar xzf fsdb2fst-src.tar.gz
export VERDI_HOME=/path/to/你的verdi
bash deploy/build_fsdb2fst.sh

          产物 /tmp/third_party/fsdb2fst/fsdb2fst，RPATH 已指向本地 Verdi 库路径，运行时零额外处理。

          ⑤ 隔离机：冒烟验证

          /tmp/third_party/fsdb2fst/fsdb2fst --info 你的.fsdb 2>&1 | head

          ⑥ MCP 配置

          "env": { "FSDB2FST_BIN": "/tmp/third_party/fsdb2fst/fsdb2fst" }

          $FSDB2FST_BIN 是第一优先命中，指过去后既不依赖自动编译、也不依赖隔离机有没有源码。

          ⑦ 端到端验证

          重启 MCP，再跑一次 prepare_session 喂 .fsdb。「找不到 fsdb2fst」应消失，转出 .fst + .fst.hier（两文件成对，缺 .hier 打不开）。

          4常见坑速查 踩坑

          报错信息里有一行 Why not built automatically:，它会精确告诉你卡在哪一步

          症状原因解法
          sources are not shipped in the PyPI packagepip 包 < 0.2.6 缺源码本流程手动补源码
          g++ 4.8 报一堆语法错老 CentOS 7 默认 gcc，不支持 C++17devtoolset-9 或换 g++ ≥ 7
          libnffr.so: cannot open shared object运行时找不到库在隔离机本地编（RPATH 指向本地）；否则两个 .so 放二进制同目录
          「no Verdi FsdbReader runtime」MCP 进程里没 VERDI_HOMEMCP 配置 env 里显式加 VERDI_HOME（或直接 FSDB2FST_BIN 绕过）
          --info 无输出 / 报错fsdb 损坏或路径错先确认 fsdb 能被 Verdi 正常打开
          一句话定位

          报错信息是设计好用来定位的——先看 Why not built automatically: 那一行，再对号入座；别一上来就重装，多数情况是「源码 / 库 / g++ / env」四选一缺了。
