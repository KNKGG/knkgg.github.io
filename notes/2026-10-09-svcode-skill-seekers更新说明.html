                    svcode-skill-seekers 更新：从扁平解析到跨文件层次树

                    之前只能告诉你「每个文件里有哪些类和方法」，现在能回答「DUT 的模块层次长什么样」「这个类往上继承谁」——两层演进把验证工程师最常 grep 的两件事做成了开箱即用的索引
                    版本：v0.2.0 → v0.4.0 · 源码 ~/svcode-skill-seekers/ · 解析器 tree-sitter-systemverilog · 信息截至 2026-10

                    1更新解决了什么动机

                    把「文件内扁平信息」升级成「跨文件层次视图」

                    上一版（v0.2.0）已经把「单个文件里有什么」做全了——9 类顶层容器（module / interface / program / package / class / interface_class / checker / config / primitive）+ 7 类嵌套，每个 module 的 instances 也带上了 {type, name}。

                    但那些 instances[].type 只是孤立的字符串：它告诉你 top 里实例化了一个 fifo，却不告诉你这个 fifo 定义在哪个文件、它自己又实例化了什么。想查「DUT 层次」或「TB 类继承」，只能打开多个文件手动 grep 拼。

                    这一版补的就是这块空白：建立跨文件的全局层次视图，覆盖三类容器、两类关系：

                    • 实例化关系（module + interface）：instances[].type → 链接到被实例容器定义，递归成树；
                    • 继承关系（class + interface_class）：base_classes[] → 链接到基类定义，成继承链；
                    • 端口对齐：位置连接 (clk, rst_n, count) 的第 N 项 → 被实例模块定义 ports 的第 N 个端口名，补全 name。
                    一句话对比

                    之前：一张张互不相连的「零件清单」，每张只写自己这间屋子里有什么。

                    现在：一份「装配图」+「族谱」，从顶层往下能递归看到谁装了谁，从子类往上能追到根类。

                    2版本演进：两张「层」路线

                    0.2.0 打底子，0.3.x 补「面」，0.4.0 补「体」

                    版本做的事性质
                    0.2.0支持所有 SystemVerilog 容器类型（9 顶层 + 7 嵌套），tree-sitter 真实 AST容器类型打底
                    0.3.0schema 从 classes 重构为 containers，为多容器类型让路数据结构
                    0.3.5第一层：实例化的「面」——端口连接 + 参数覆盖文件内信息补全
                    0.4.0第二层：实例化的「体」——跨文件层次树 + 继承链 + 端口对齐跨文件关系

                    「层」这个说法是从验证的角度借来的：第一层解决「一个实例化长什么样」（面），第二层解决「这个实例化在整个 DUT 里处于什么位置、连到谁」（体）。两层合起来，才把一个 instances[].type 字符串，从「名字」变成「图上的一个节点」。

                    3第一层：给实例化补「面」0.3.5

                    一个 module 实例化，除了名字，还有参数和端口这两样「面」信息

                    早期 _instances 只提取 {type, name}——知道实例化了什么、叫什么，却不知道参数怎么覆盖、端口怎么连。第一层补的就是这两样。

                    3.1 端口连接：命名 vs 位置

                    SV 端口连接有两种写法，语义完全不同：

                    // 命名连接：端口名显式写出来，和顺序无关
fifo u_fifo(.clk(clk), .rst_n(rst_n), .din(d), .dout(d));

// 位置连接：只写表达式，按端口声明顺序对应
fifo u_fifo(clk, rst_n, d, d);

                    提取时两者分开处理：命名连接直接拿到端口名 .clk(...) → name="clk"；位置连接没有名字，暂时记 name=null，只留 connection 表达式——位置连接的端口名要等第二层「对齐」才能补上（见 4.3）。

                    3.2 参数覆盖 #(.W(16))

                    参数覆盖 #(.W(16), .DEPTH(8)) 也一样，从 parameter_value_assignment 节点里把每个 命名参数 = 值 对抽出来：

                    counter #(.W(8)) u_count (clk, rst_n, d);
// → params = [{"name": "W", "value": "8"}]

                    这样 instances 从扁平的 {type, name} 变成了 {type, name, params, ports}——「面」的信息齐了。

                    4第二层：跨文件层次树0.4.0 · 核心

                    新增 hierarchy.py，把散在各文件的容器串成图

                    4.1 全局容器索引

                    跨文件链接的第一步，是把所有文件的所有容器汇总成一个索引：

                    # index[(kind, name)] -> [(file, container), ...]  # list 因为可能重名
# 纳入的 kind：module / interface（实例化侧）；class / interface_class（继承侧）

                    有了它，instances[].type 和 base_classes[] 这些「名字」就能查到「定义在哪个文件、长什么样」，从字符串变成指针。

                    4.2 两类关系，两种树

                    第二层解析两类引用关系，分别构树：

                    • 实例化树（module + interface）：根 = 索引里没有被任何实例引用的容器（多顶层时 DUT top 和 TB top 并列）；从根递归展开，visited 集合防环；悬空实例（外部 IP）作为叶子标 (external)。
                    • 继承（class + interface_class）：每条 extends 链向上追到根（或 uvm_object），同时按基类分组出「向下」的直接子类列表。
                    # 实例化树渲染结果（references/hierarchy.md）
top (module) [top.sv]
├─ u_count : counter (module)  [counter.sv]
├─ u_fifo  : fifo (module)    [fifo.sv]
│   └─ u_sram : sram (module) [sram.sv]
├─ bus_i   : bus_if (interface) [bus_if.sv]
└─ u_ext   : external_ip  (external)

# 继承链
my_driver → uvm_driver → uvm_component → uvm_object → uvm_void

                    4.3 位置连接还原端口名

                    第一层留下的 name=null 位置连接，这里按顺序对齐到被实例模块的定义端口：第 N 个位置连接 → 定义 ports 的第 N 个端口名。

                    counter #(.W(8)) u_count (clk, rst_n, d);
// counter 定义 ports = [clk, rst_n, count]
// 位置连接对齐后：
//   (clk, rst_n, d) → clk / rst_n / count

                    端口数不匹配时，超出部分保持 name=null 并标 unmatched。对齐结果直接写回 instances[].ports[].name，所以 code_analysis.json 里也能看到补全后的端口名。

                    引用解析结果分三类落账：resolved（唯一命中）/ ambiguous（重名多个候选）/ unresolved（找不到，外部 IP）。后两类单独列在 hierarchy 报告里，不硬塞进树。

                    输出三件套

                    code_analysis.json 顶层多一个 hierarchy 字段（结构化底稿）→ references/hierarchy.md（完整树，Claude 按需读）→ SKILL.md 加「层次概览」小节（顶层模块、树数、继承根）。查层次读一个文件即可，不用再 grep。

                    5三个诚实边界坑

                    tree-sitter 给的是语法树，不是语义；有些东西它分不出来，这些是已知边界

                    5.1 scoped 基类：uvm_pkg::uvm_packer

                    UVM 的 compat 层里有 class uvm_compat_packer extends uvm_pkg::uvm_packer;——基类是「作用域限定名」。初版 _class_base 只取第一个 simple_identifier，会错取成 uvm_pkg（那是 package 不是 class）。

                    修法：取 class_type 里最后一个 simple_identifier（scoped 名的末段），同时参数化基类 extends uvm_driver #(T) 里的参数在深层 parameter_value_assignment、不是直接子节点，不受影响。修完 uvm_compat_packer 的链从错误的 [..., uvm_pkg] 变成正确的 [uvm_compat_packer, uvm_packer, uvm_policy, uvm_object, uvm_void]。

                    5.2 参数化继承：extends BASE

                    class uvm_reg_sequence #(type BASE=uvm_sequence) extends BASE; 和 virtual class uvm_port_base #(type IF=uvm_void) extends IF; 里，BASE / IF 是 type 参数，不是真实类名。tree-sitter 只能告诉你是 extends BASE，无法静态解析出 BASE 到底被绑成哪个类——这是参数化继承的固有边界，继承链会如实停在 BASE 这一层，标注清楚，不假装解析。

                    5.3 增量 update 的端口对齐「陈旧」

                    端口对齐结果写进 ports[].name 持久化后，位置连接原本 name=null 的语义被覆盖了。于是增量 update 时，如果被实例模块改了端口名、而实例文件本身没变（位置连接本来就不用改调用方代码），复用的旧文件会带着旧端口名。

                    修法：第一层给位置连接打 positional: true 标记，对齐前先把这些项的 name 还原为 null 再重算——幂等可重算，增量重跑永远对齐到最新定义端口。这也顺带让旧数据（无标记、name=null）靠 name is None 兜底，向后兼容。

                    6.2 skill 大小随复杂度的增长

                    一个常被问的问题：DUT 越复杂，skill 会不会爆炸。实测结论是线性增长 O(N)，N ≈ 容器 + 方法 + 端口 + 信号 + 实例化总数，没有平方项。主导项不是 markdown，而是 code_analysis.json（占 ~72%）——它是全量结构化数据，JSON 字段重复 + 缩进带来 ~1.5–2× 冗余。

                    放大系数取决于 docstring 密度，而非代码量本身——工具只存签名 + 结构 + docstring，不存实现体：

                    • 文档密集的 class 库（UVM）：skill ≈ 源码的 1.25×（145 文件 → 3.4 MB）；
                    • 实现密集、注释稀少的 RTL：放大系数更低，单个典型 module 实测 json 约几 KB；
                    • 实际验证 DUT 是 block / 子系统级（几百 module），skill 落在几 MB 到几十 MB，可控；完整 SoC（几万 module）不建议整建，按 block 拆。
                    一句话总结

                    这一版把 svcode-skill-seekers 从「文件内解析器」升级成「跨文件索引器」——第一层补实例化的面（端口/参数），第二层建实例化的体（层次树/继承链/端口对齐）。验证工程师查 DUT 层次和 TB 继承，终于不用再 grep 多文件手动拼了。
